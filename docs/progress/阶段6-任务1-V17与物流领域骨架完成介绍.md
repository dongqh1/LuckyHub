# 阶段 6 任务 1：V17 与物流领域骨架完成介绍

## 为什么需要这个任务

现金订单、积分兑换和抽奖实物权益都需要收货地址、不可变地址快照、统一发货单、物流轨迹和回调防重。如果三条来源各自保存一套物流状态，幂等、隐私和状态约束会分散且容易不一致。V17 因此先建立一个覆盖三类来源的物流聚合，为后续领取、履约和回调服务提供共同的数据边界。

## 具体完成了什么

- 新增 `V17__add_shipping_and_physical_claim.sql`，V1–V16 保持不变。
- 新增 `user_shipping_address`、`shipping_address_snapshot`、`shipping_order`、`shipping_tracking_event`、`shipping_callback_receipt` 五张表。
- 地址簿和地址快照只保存六项加密 `TEXT` 及三项有界脱敏展示字段；回调只保存 nonce 和签名摘要，不保存原文或供应方响应。
- 用 CHECK 约束固定来源、地址、发货、轨迹和回调状态；用唯一索引固定快照号、来源身份、发货号、履约号、领取请求、运单号、供应方事件和回调身份。
- `user_benefit` 增加领取期限、领取时间和发货单身份，并为既有 `CLAIM_PENDING` 权益补七天领取期限；现金订单和积分兑换单增加可空的地址快照与发货单身份。
- 库存流水新增 `CLAIM_RETURN`，用于以后实物权益领取或履约失败时的补偿边界。
- 新增五个实体、五个 Mapper、四组业务枚举和 `53001`–`53012` 稳定安全错误码；锁查询使用显式 `FOR UPDATE`。
- 新增 `shipping:address:manage`、`shipping:read`、`shipping:operate` 权限，并按 USER/ADMIN 边界授权。

## 来源幂等示例

抽奖权益 `user_benefit.id=8801` 创建发货单时使用：

```text
source_type = LOTTERY_BENEFIT
source_id   = 8801
```

`shipping_order(source_type, source_id)` 的唯一键保证同一权益即使因网络重试重复请求，也只能对应一张发货单。现金订单和积分兑换分别使用 `CASH_ORDER`、`POINTS_REDEMPTION` 进入同一聚合；不会创建独立的 LOGISTICS 履约任务。

## 边界与下一步

本任务只交付持久化和领域骨架，不实现地址 API、权益领取、发货编排、物流供应方调用或回调处理，也不保存明文 PII、原始回调秘密或供应方响应。下一任务将在这些契约上实现地址簿的加密读写与访问控制。
