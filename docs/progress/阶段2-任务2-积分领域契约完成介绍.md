# 阶段 2 · 任务 2：积分领域契约完成介绍

## 1. 这一步完成了什么

V10 已经建立数据库表，本任务继续建立与这些表一一对应的 Java 领域契约，包括：

- 4 组枚举和稳定错误码；
- 3 个数据库实体；
- 3 个 MyBatis-Plus Mapper；
- 7 个命令或查询 DTO；

这些类型是后续积分账户服务、并发测试、积分兑换事务和 API 的共同语言。本任务还没有实现积分增减业务逻辑。

## 2. 积分业务枚举

### 2.1 `PointsBusinessType`：积分为什么变化

| 枚举值 | 含义 | 当前阶段是否使用 |
| --- | --- | --- |
| `LOTTERY_REWARD` | 抽奖奖励积分 | 后续阶段预留 |
| `ORDER_REWARD` | 商城订单奖励积分 | 后续阶段预留 |
| `MEMBERSHIP_BONUS` | 会员奖励积分 | 后续阶段预留 |
| `REDEMPTION` | 积分兑换扣减 | 阶段 2 使用 |
| `REVERSAL` | 兑换或扣减冲正 | 阶段 2 使用 |
| `MANUAL_ADJUSTMENT` | 管理员人工调整 | 阶段 2 使用 |

业务类型和业务编号组合后形成幂等身份。例如：

```text
REDEMPTION + REDEEM-20260808-001
```

这表示一笔确定的兑换扣分业务，客户端重复发送时仍然指向同一笔积分变化。

### 2.2 `PointsDirection`：积分向哪个方向变化

只有两个值：

- `CREDIT`：增加积分；
- `DEBIT`：扣减积分。

流水中的 `amount` 永远表示正数，方向单独保存。例如管理员增加 500 分：

```text
direction = CREDIT
amount = 500
```

用户兑换商品扣减 3000 分：

```text
direction = DEBIT
amount = 3000
```

不使用 `amount = -3000` 的好处是避免“双重负号”一类歧义，例如 `DEBIT -3000` 到底应该扣减还是增加。后续服务统一根据方向处理正数金额。

### 2.3 `PointsRedemptionStatus`：兑换状态

```text
PROCESSING -> COMPLETED -> REVERSED
```

- `PROCESSING`：事务正在创建兑换；
- `COMPLETED`：积分和库存均已确认；
- `REVERSED`：后来发生业务失败，积分与库存已完成补偿。

## 3. 三个数据库实体和 Mapper

### 3.1 `PointsAccount`

映射 `points_account`，主要字段为用户、余额、版本号和更新时间。

### 3.2 `PointsLedger`

映射 `points_ledger`，保存业务身份、方向、数量、变化后余额、原扣减流水和备注。

### 3.3 `PointsRedemptionOrder`

映射 `points_redemption_order`，保存兑换身份、用户、SKU、数量、积分价格、商品快照、状态和冲正信息。

三个 Mapper 均继承 MyBatis-Plus 的 `BaseMapper`，并已将以下包加入统一扫描：

```text
com.dongqh.luckyhub.points.mapper
```

这使后续服务能够通过依赖注入查询和写入积分数据，而不需要重复配置 Mapper Bean。

## 4. 命令和查询对象

### 4.1 内部记账命令

- `PointsMutationCommand`：表达一次增加或扣减；
- `PointsReversalCommand`：表达对原扣减流水的冲正。

它们只表达领域数据，不负责直接修改数据库。

### 4.2 管理员积分调整

`AdminPointsAdjustmentCommand` 使用有符号 `delta` 表达管理员意图：

```text
delta = 500   表示增加 500 分
delta = -300  表示扣减 300 分
```

它明确拒绝：

- `delta == 0`：没有实际变化，不应生成流水；
- `delta == Long.MIN_VALUE`：对该数取绝对值会溢出 Java `long`。

后续服务会把正负 `delta` 安全转换成 `CREDIT/DEBIT + 正数 amount`。

### 4.3 兑换和查询输入

- `CreatePointsRedemptionCommand`：兑换单号、SKU、数量 1–100；
- `ReversePointsRedemptionCommand`：冲正单号和原因；
- `PointsLedgerQuery`：按业务类型、业务编号和方向分页查流水；
- `PointsRedemptionQuery`：按兑换状态分页查兑换单。

两个分页查询默认：

```text
page = 1
size = 20
最大 size = 100
```

## 5. 为什么返回视图使用不可变 record

三个返回视图分别是：

- `PointsAccountView`；
- `PointsLedgerView`；
- `PointsRedemptionView`。

它们使用 Java `record`，创建后字段不能被重新赋值，适合表达服务向 API 返回的只读快照。

### `balanceAfter` 示例

假设用户原有 5000 分：

```text
流水 1：DEBIT 3000，balanceAfter = 2000
流水 2：CREDIT 500，balanceAfter = 2500
```

`balanceAfter` 不是当前账户余额的动态引用，而是“这笔流水完成后，当时的余额”。即使用户后来又获得积分，流水 1 的 `balanceAfter` 仍然是 2000。这样可以按时间顺序重建余额变化并发现异常。

## 6. 稳定错误码 `47001–47009`

| 错误码 | 场景 |
| --- | --- |
| `47001` | 积分余额不足 |
| `47002` | 相同幂等编号对应了不同参数 |
| `47003` | 原积分流水不存在 |
| `47004` | 积分冲正状态冲突 |
| `47005` | 积分数量不合法 |
| `47006` | 积分兑换单不存在 |
| `47007` | SKU 不能用于积分兑换 |
| `47008` | 兑换单状态冲突 |
| `47009` | 用户不存在或已禁用 |

错误码同时固定了中文提示和 HTTP 状态。后续服务和 API 只需引用枚举，不需要各自定义不同的错误语义。

## 7. 权限常量

`PermissionCodes` 新增：

