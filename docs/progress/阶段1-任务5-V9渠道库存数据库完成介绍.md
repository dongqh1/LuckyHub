# 阶段 1 · 任务 5：V9 渠道库存数据库完成介绍

## 1. 这一步解决了什么问题

同一件商品以后可能同时出现在多个业务中：

- 在抽奖活动中作为实物奖品；
- 在积分商城中供用户兑换；
- 在普通商城中用现金购买；
- 在限时活动中单独投放。

如果所有业务只共同修改一个“剩余库存”，很容易出现超卖。例如商品只有 100 件，但抽奖系统认为自己有 80 件，积分商城也认为自己有 80 件，最终可能承诺发出 160 件。

V9 数据库迁移建立了渠道库存底座，将库存拆成“SKU 总库存”和“各业务渠道分到的库存”，并为预占、确认、释放和审计流水预留标准数据结构。

## 2. 新增的四张表

### 2.1 `sku_inventory`：SKU 总库存

记录某个 SKU 实际可以投入业务的库存总量，以及已经分配给各渠道的数量。

重要字段：

- `sku_id`：对应商品 SKU；
- `total_stock`：总库存；
- `allocated_stock`：已经分配给渠道的库存；
- `version`：后续并发更新使用的版本号。

数据库保证：

```text
allocated_stock <= total_stock
```

也就是说，总共只有 100 件时，所有渠道合计最多只能分配 100 件。

### 2.2 `inventory_channel_stock`：渠道库存

记录一个 SKU 在某个渠道中的库存状态。

重要字段：

- `channel_code`：渠道编码，例如 `LOTTERY`、`POINTS_MALL`；
- `allocated_stock`：这个渠道一共分到多少件；
- `available_stock`：当前还能使用多少件；
- `reserved_stock`：已经被用户操作占住、但还未最终消费的数量；
- `consumed_stock`：已经确认消费的数量。

数据库强制满足：

```text
allocated_stock = available_stock + reserved_stock + consumed_stock
```

这个等式可以防止库存凭空增加或消失。

### 2.3 `inventory_reservation`：库存预占

记录一次具体业务对库存的临时占用。

预占状态只有三种：

| 状态 | 含义 |
| --- | --- |
| `RESERVED` | 已占住库存，等待业务最终结果 |
| `CONFIRMED` | 业务成功，库存正式消费 |
| `RELEASED` | 业务取消，库存已经退回可用数量 |

每个 `reservation_no` 全局唯一，防止相同请求被重复处理。

### 2.4 `inventory_ledger`：不可变库存流水

记录库存为什么发生变化，支持后续审计和问题排查。

流水操作包括：

- `INITIALIZE`：初始化 SKU 总库存；
- `ALLOCATE`：向业务渠道分配库存；
- `RESERVE`：预占库存；
- `CONFIRM`：确认消费；
- `RELEASE`：释放预占。

每个 `business_no` 全局唯一。后续即使客户端因为网络超时重复发送请求，也可以根据业务号识别是否已经处理，避免重复加减库存。

## 3. 一个完整例子

假设“空气炸锅标准款”这个 SKU 有 100 件库存。

### 第一步：初始化总库存

```text
total_stock = 100
allocated_stock = 0
```

此时 100 件都还没有分配给具体业务。

### 第二步：分配渠道库存

给抽奖渠道 30 件，给积分商城 50 件：

```text
SKU 总库存：100
已分配库存：80
尚未分配：20

LOTTERY：allocated=30, available=30, reserved=0, consumed=0
POINTS_MALL：allocated=50, available=50, reserved=0, consumed=0
```

抽奖系统最多只能使用自己的 30 件，不能消耗积分商城的 50 件。

### 第三步：用户中奖后预占 1 件

用户抽中空气炸锅时，先在 `LOTTERY` 渠道预占：

```text
LOTTERY：allocated=30, available=29, reserved=1, consumed=0
```

为什么不直接算成已消费？因为后面可能还需要用户填写地址、进行资格校验或处理异常。

### 第四步：确认或释放

如果领奖成功：

```text
LOTTERY：allocated=30, available=29, reserved=0, consumed=1
```

如果领奖取消：

```text
LOTTERY：allocated=30, available=30, reserved=0, consumed=0
```

前者对应 `CONFIRMED`，后者对应 `RELEASED`。每一步都会有独立流水，能够查清库存变化原因。

## 4. 数据库提供的安全保护

V9 已建立以下保护：

- 一个 SKU 只能有一条总库存记录；
- 同一个 SKU 在同一渠道只能有一条渠道库存记录；
- 预占单号不能重复；
- 库存流水业务号不能重复；
- 已分配总量不能超过 SKU 总库存；
- 渠道分配量必须等于可用、预占和已消费数量之和；
- 预占和流水数量必须大于 0；
- 预占状态和流水操作只能使用约定值；
- 所有库存数量使用无符号整数，不能存入负数；
- 时间字段保留毫秒精度。

## 5. 当前边界

本任务只完成数据库结构和迁移契约，还没有开放库存接口，也没有实现实际的库存加减服务。

因此当前阶段：

- 不会自动给商品初始化库存；
- 不会在中奖或积分兑换时自动预占；
- 不会自动确认或释放库存；
- 不会直接处理并发请求。

这些行为由接下来的 Task 6“幂等渠道库存服务”和 Task 7“库存管理 API”实现。

V9 也没有修改旧的抽奖活动奖品库存服务，两套库存暂时保持独立，避免尚未完成迁移时影响现有抽奖主链路。
