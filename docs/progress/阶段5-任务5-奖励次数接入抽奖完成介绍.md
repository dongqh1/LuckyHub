# 阶段 5 · 任务 5：奖励次数接入真实抽奖

## 为什么账户完成后还要接入抽奖流程

任务 4 只是让奖励次数“有余额”。如果抽奖入口仍只看活动免费额度，用户虽然看得到奖励次数，却无法真正使用。本任务把 MySQL 奖励次数和 Redis 高频抽奖额度组合成一个完整生命周期。

## 具体实现

1. 从抽奖资格快照生成唯一的上海日期，MySQL 预留和 Redis 额度使用同一天，避免午夜边界不一致。
2. 在已有的用户/活动分布式锁内先预留奖励次数，再预留 Redis 额度。
3. Redis 的有效每日上限等于“活动免费上限 + 当天累计有效奖励预留”。
4. Redis 额度不足或不可用时，立即释放 MySQL 奖励次数。
5. MySQL 建立抽奖订单失败时，同时释放 Redis 额度和奖励次数。
6. `DRAW_CONFIRMED` 消息依次确认 Redis 和奖励次数；`DRAW_RELEASE_REQUESTED` 依次释放两者。
7. 两套确认/释放都可重复执行，消息重投不会重复扣减或退回。
8. 定时修复任务在原有 Redis/订单修复后，再按真实订单状态修复奖励次数预留。
9. 兼容阶段 5 之前的历史消息：如果旧消息没有对应奖励次数预留，不会阻断原有 Redis 结算。

## 为什么 Redis 仍记录完整抽奖次数

假设活动每天免费 1 次，用户有 9 次奖励，发起十连抽：

```text
MySQL 奖励账户：预留 9 次
Redis 有效上限：1 + 9 = 10
Redis 本次计数：仍然增加完整的 10 次
```

Redis 的职责是回答“用户今天一共抽了多少次”，所以必须记 10，而不是只记免费部分 1。MySQL 奖励账户负责解释新增上限中的 9 次来自哪里。

如果 Redis 只增加 1，用户当天可能再次利用相同上限抽奖，形成额度漏洞。

## 失败补偿举例

用户有 2 次奖励，发起十连抽，但活动免费上限加奖励后仍不足 10：

```text
预留前：可用 2，预留 0
MySQL 先预留：可用 0，预留 2
Redis 判断总上限不足，拒绝十连抽
系统立即释放：可用 2，预留 0
```

用户不会因为一次被拒绝的抽奖丢失奖励次数。

## 验证结果

- 单元测试验证奖励预留先于 Redis、累计奖励提高有效上限、Redis 失败释放奖励。
- Redis 额度、消息消费、定时修复和旧抽奖流程回归通过。
- 真实 MySQL + Redis 测试验证“1 次免费 + 9 次奖励”可以完成十连抽，Redis 计数为 10，MySQL 预留为 9。
- 建单失败会同时释放两类预留，相同请求重试保持幂等。
