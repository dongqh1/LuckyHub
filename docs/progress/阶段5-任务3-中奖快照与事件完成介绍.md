# 阶段 5 · 任务 3：中奖快照与兼容事件

## 为什么需要这个任务

任务 2 解决了“抽奖前应该发什么”，任务 3 解决“中奖后永远以哪一份内容为准”。如果中奖记录只保存奖励定义 ID，管理员后续修改定义时，历史中奖可能被错误地按新内容发放。

因此中奖发生的一瞬间，系统要把奖励完整冻结，并在同一个数据库事务里写入中奖记录、用户权益和待发送消息。

## 具体实现

1. `DrawResultItem` 携带可空的 `RewardSnapshot`，旧八参数构造器继续可用。
2. 中奖记录保存奖励定义 ID、奖励类型、目标 ID、数量、JSON 载荷和指纹。
3. 用户权益保存完全相同的六项快照数据。
4. 两份数据与抽奖订单成功状态、库存扣减、Outbox 消息处于同一事务：任何一步失败都会整体回滚。
5. 履约事件增加 `rewardDefinitionId`、`rewardType` 和 `rewardFingerprint`。
6. 事件只接受“新三字段全部存在”或“全部为空”，拒绝只有一部分身份的危险事件。
7. 保留原来的四参数事件构造器，历史未绑定奖品仍能走旧流程。

## 举例理解

用户中奖时，冻结的优惠券奖励是：

```json
{
  "rewardDefinitionId": 701,
  "rewardType": "COUPON",
  "rewardTargetId": 702,
  "rewardQuantity": 2,
  "rewardPayload": {
    "templateId": 702,
    "templateCode": "WELCOME",
    "quantity": 2
  },
  "rewardFingerprint": "bbbb...bbbb"
}
```

中奖记录和用户权益各保存一份内容相等的副本，履约事件携带定义 ID、类型和指纹。消费消息时可以把事件与数据库两份事实交叉核对。

假设中奖后管理员把 `WELCOME` 奖励从 2 张改为 1 张，这次历史中奖仍然发 2 张，因为履约使用的是中奖时冻结的快照，而不是当前奖励定义。

## 旧奖品示例

```text
rewardDefinitionId = null
rewardType = null
rewardFingerprint = null
```

这三个值全空表示历史奖品。事件仍包含原来的 `benefitId`、`drawRecordId`、`prizeId` 和 `prizeType`，旧消费者能够继续读取。

## 验证结果

- 验证中奖记录和权益六项奖励字段相等。
- 验证履约事件携带相同的定义 ID、类型和指纹。
- 验证旧中奖的奖励字段全部为空。
- 验证事件身份部分缺失时立即拒绝。
- 抽奖事务、Outbox、抽奖服务、持久化契约和控制器组合测试共 38 项，全部通过。
