# 阶段 5 · 任务 4：奖励抽奖次数账户

## 为什么要有独立账户

“额外抽奖次数”不能只写在中奖说明里。它需要像积分一样有余额、有流水，并能处理并发、重试和抽奖中途失败。

本任务建立了三个概念：

- 账户：当前可用多少次、正在被抽奖请求预留多少次。
- 预留：某个抽奖请求临时占用了多少奖励次数。
- 不可变流水：每一次奖励入账、成功消费和失败退回都留下凭证。

## 具体实现

1. `credit` 把奖励次数记入账户，同一业务 ID 重试不会重复入账，数量变化则判定为身份冲突。
2. `reserve` 按请求 ID 创建预留，把可用余额移动到预留余额；即使余额为 0 也保存请求身份，保证重试可以核对。
3. `confirm` 在抽奖成功后从预留余额正式消费，只生成一次消费流水。
4. `release` 在抽奖失败后把预留余额退回可用余额，只生成一次退回流水。
5. 已确认和已释放是互斥终态，不能把一次已成功抽奖再退回。
6. 所有余额修改都使用 MySQL `FOR UPDATE` 行锁和精确整数运算。
7. 过期预留会读取真实抽奖订单状态：订单成功就确认，订单失败就释放，处理中订单不擅自处理。
8. 20 个线程同时预留 10 次余额时，最终最多只有 10 次被预留，账户不会出现负数。

## “1 次免费 + 2 次奖励”举例

假设某活动每天免费 1 次，用户账户还有 2 次奖励次数。

```text
开始：可用奖励 2，预留奖励 0
用户请求抽 3 次
免费额度承担 1 次，奖励账户预留 2 次
预留后：可用奖励 0，预留奖励 2
```

如果抽奖成功：

```text
确认后：可用奖励 0，预留奖励 0
新增 DRAW_CONSUME 流水 2 次
```

如果抽奖执行失败：

```text
释放后：可用奖励 2，预留奖励 0
新增 DRAW_RELEASE 流水 2 次
```

用户用相同请求 ID 重试时，系统读取原预留，不会再占用 2 次。

## 为什么余额为 0 也要保存预留

第一次请求余额为 0 时，如果什么都不保存，第二次相同请求可能在账户刚好入账后错误地占用新余额，导致同一请求前后身份不一致。保存一条 `bonusReserved=0` 的预留后，重试会得到与第一次相同的结果。

## 验证结果

- 入账幂等、身份冲突、预留、确认、释放、零余额预留和终态冲突测试通过。
- 真实订单状态驱动的过期预留修复测试通过。
- 20 路并发预留测试连续运行两次通过，没有超扣或负余额。
