# 阶段 2 · 任务 6：积分兑换事务完成介绍

## 1. 完成内容

本任务把商品、积分账户、POINTS 渠道库存和兑换单连接成一个可执行的积分兑换流程，新增：

- 可兑换 SKU 快照查询；
- `PointsRedemptionService` 创建、详情、分页和管理员冲正；
- `PROCESSING -> COMPLETED -> REVERSED` 兑换状态机；
- 兑换编号幂等与用户数据隔离；
- 20 路重复兑换并发保护；
- 积分、库存、订单跨服务同事务回滚。

## 2. 3000 积分兑换示例

用户有 5000 积分，POINTS 渠道有 1 件商品，单价 3000 积分：

```text
兑换编号：REDEEM-3000
SKU：1001
数量：1
总积分：3000 × 1 = 3000
```

事务严格按以下顺序执行：

```text
认领 PROCESSING 兑换单
-> POINTS 渠道预占 1 件
-> 扣除 3000 积分
-> 确认库存消费
-> 兑换单改为 COMPLETED
```

结果：用户余额 2000，库存 consumedStock 增加 1，产生一笔 REDEMPTION 扣分流水和一张 COMPLETED 兑换单。

## 3. 为什么先创建 PROCESSING 订单

`redemptionNo` 是兑换流程的唯一业务身份。事务首先执行 `INSERT IGNORE` 认领兑换单，只有认领成功的事务继续修改库存和积分。

如果 20 个请求同时使用相同兑换编号，其他请求等待获胜事务提交后读取同一张订单。因此最终只有：

```text
兑换单：1 张
REDEMPTION 扣分流水：1 条
库存预占：1 条
RESERVE 流水：1 条
CONFIRM 流水：1 条
实际消费库存：1 件
```

如果同一编号被改成其他用户、SKU 或数量，返回 `47002`，不能借幂等编号修改另一笔资产。

## 4. 商品快照

兑换单保存创建当时的：商品编码、商品名、SKU 编码、SKU 名称、商品类型、图片、积分单价和总积分。

例如兑换完成后商品改名并从 3000 分调价到 9999 分，历史兑换仍显示原名称和 3000 分，不会重写历史交易。

目录服务只在商品和 SKU 均启用、`pointsEnabled=true` 且积分价格大于 0 时返回快照；不可兑换 SKU 返回 `47007`。

总价使用 `Math.multiplyExact`，数量乘价格溢出时返回稳定的 `47005`，不会把 Java 算术异常暴露给接口。

## 5. 原子回滚

所有创建步骤加入同一个 MySQL `READ_COMMITTED` 事务：

- 积分不足：兑换单、库存预占和相关流水全部回滚；
- 库存不足：兑换单和积分变化全部回滚；
- 扣分后库存确认异常：扣分、预占、订单与流水全部回滚；
- 状态更新失败：前面的积分和库存变化同样回滚。

因此不存在“积分扣了但没有商品”或“商品消耗了但没有扣积分”的半成品。

## 6. 冲正

管理员冲正一张 COMPLETED 兑换单时，同一事务执行：

```text
锁定兑换单
-> 新增 REVERSAL 加分流水并关联原扣分流水
-> CONFIRMED 库存反向恢复为 REVERSED
-> 兑换单改为 REVERSED 并记录冲正编号和原因
```

原订单、原扣分流水和原库存预占都不会删除。相同冲正编号可安全重试；同一订单换另一个冲正编号再次处理返回 `47008`。

## 7. 用户隔离

详情和分页查询必须传入当前登录用户 ID。详情属于其他用户时返回 `20001`，分页查询始终附加当前用户条件，无法通过参数查询别人的兑换记录。
