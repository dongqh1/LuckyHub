# 阶段 2 · 任务 3：幂等积分账户服务完成介绍

## 1. 这一步完成了什么

本任务把 V10 的积分账户和流水表真正连接成可用的领域服务，实现：

- 查询用户当前积分；
- 奖励积分入账；
- 积分兑换扣减；
- 管理员人工增加或扣减；
- 对兑换扣减执行单次冲正；
- 相同业务请求幂等返回；
- 幂等编号被不同参数复用时拒绝处理；
- 余额不足、加法溢出、无效用户时整笔事务回滚。

服务接口为 `PointsAccountService`，所有资产修改使用 MySQL `READ_COMMITTED` 短事务。

## 2. 一个积分账户如何创建

积分账户采用“按需创建”：有效用户第一次发生积分变化时执行：

```sql
INSERT INTO points_account(user_id, balance, version, created_at, updated_at)
VALUES (?, 0, 0, CURRENT_TIMESTAMP(3), CURRENT_TIMESTAMP(3))
ON DUPLICATE KEY UPDATE user_id = ?;
```

`user_id` 有唯一索引，因此两个请求同时为同一用户创建账户时，最终也只有一行。Task 4 的并发测试进一步发现，原先的 `INSERT IGNORE` 在高并发下可能产生锁升级死锁；重复键更新现在还承担了按用户锁定账户的职责，完整原因见 Task 4 介绍。

仅仅查询一个尚未发生积分变化的有效用户时，服务返回：

```text
balance = 0
updatedAt = null
```

此时不会为了查询而创建空账户。

## 3. 加分示例

假设用户当前没有积分，管理员补发 1000 分：

```text
业务类型：MANUAL_ADJUSTMENT
业务编号：ADJUST-CREDIT
方向：CREDIT
数量：1000
变化后余额：1000
```

账户更新使用带溢出保护的条件 SQL：

```sql
UPDATE points_account
SET balance = balance + :amount, version = version + 1
WHERE user_id = :userId
  AND balance <= 9223372036854775807 - :amount;
```

如果当前余额再加本次数量会超过 Java/MySQL 有符号 `BIGINT` 最大值，更新行数为 0，服务返回 `47005`，不会产生流水。

奖励入账只允许以下类型：

- `LOTTERY_REWARD`；
- `ORDER_REWARD`；
- `MEMBERSHIP_BONUS`。

`MANUAL_ADJUSTMENT` 只能通过管理员调整入口使用，避免普通奖励流程伪装成人工调整。

## 4. 扣分和余额不足示例

用户原有 700 分，用 500 分兑换商品：

```text
原余额：700
业务类型：REDEMPTION
方向：DEBIT
扣减：500
变化后余额：200
```

扣减使用条件 SQL：

```sql
UPDATE points_account
SET balance = balance - :amount, version = version + 1
WHERE user_id = :userId
  AND balance >= :amount;
```

如果用户接着尝试扣 201 分，条件不成立：

```text
返回错误：47001 积分余额不足
账户余额：仍为 200
REDEEM-201 流水：不存在
```

因此余额不会短暂变成负数，也不会出现“扣款失败但留下流水”。

阶段 2 的直接扣减只接受 `REDEMPTION`，其他奖励类型不能调用扣减接口。

## 5. 重复请求为什么不会重复加减

每次变化使用：

```text
business_type + business_id
```

作为全局唯一业务身份。

例如抽奖系统第一次调用：

```text
LOTTERY_REWARD + LOTTERY-POINTS-1 + 用户1001 + CREDIT + 100
```

网络超时后重复发送完全相同的请求，服务会读取原流水并返回同一结果：

```text
账户只增加一次：100
积分流水只有一条
两次调用获得相同流水ID
```

如果相同业务身份被改成其他用户、其他方向或其他数量，服务返回：

```text
47002 积分幂等参数冲突
```

冲突请求中的账户创建、余额修改等数据库操作会随事务一起回滚。

## 6. 为什么先修改余额后认领流水仍然安全

积分流水需要保存准确的 `balanceAfter`，必须在账户更新后才能知道。因此事务顺序是：

```text
校验用户和命令
-> 确保账户存在
-> 查询已有业务流水
-> 条件更新账户余额
-> 读取变化后余额
-> INSERT IGNORE 认领流水
```

如果并发请求在最后一步发现流水已经被另一个事务认领，本事务会：

1. 读取获胜流水；
2. 校验用户、方向、数量等完整身份；
3. 把当前事务标记为回滚；
4. 返回获胜流水或抛出幂等冲突。

所以“输掉流水认领”的请求不会保留自己的余额变化。并发压力证明已在 Task 4 完成，并据此修复了账户锁升级死锁。

## 7. 冲正示例

用户有 1000 分，兑换扣减 300 分：

```text
原流水：REDEMPTION / DEBIT / 300 / balanceAfter=700
```

后来商品无法履约，管理员执行冲正：

```text
新流水：REVERSAL / CREDIT / 300 / balanceAfter=1000
reversalOfLedgerId -> 原扣减流水ID
```

原始扣减流水不会被更新或删除，它仍然记录当时确实发生过兑换。这样审计时可以完整看见：

```text
先扣了 300 分
后来因为履约失败退回 300 分
```

相同冲正编号重复调用会返回同一流水；如果同一笔扣减换另一个冲正编号再次处理，则返回：

```text
47004 积分冲正状态冲突
```

阶段 2 只允许冲正 `REDEMPTION` 扣减，奖励入账不能通过这个接口反向操作。

## 8. 用户有效性保护

每次查询或修改前都会读取 `sys_user`，要求：

```text
用户存在，并且 status = 1
```

用户不存在或已禁用时返回：

```text
47009 积分账户用户不存在或已禁用
```

系统不会因为收到任意数字用户 ID 就创建积分账户或流水。

## 9. 数值和输入边界

当前服务拒绝：

- 数量为 0；
- 数量为负数；
- 管理员调整值为 `Long.MIN_VALUE`；
- 加分后超过 `Long.MAX_VALUE`；
- 空业务编号或超过 100 字符的业务编号；
- 超过 500 字符的备注；
- 不符合入口要求的业务类型。

管理员负数调整通过 `Math.negateExact` 转成正数数量和 `DEBIT` 方向，避免绝对值溢出。
