## 2. 为什么选择“积分专用兑换单”

阶段 2 需要形成一个最小兑换闭环，但阶段 3 才实现优惠券、会员、现金订单和支付。

规划时比较了三种方式：

### 方式一：积分专用兑换单（采用）

```text
积分账户
  -> 积分流水
  -> points_redemption_order
  -> POINTS 渠道库存
```

优点是阶段 2 能独立查询兑换结果、保存商品价格快照、执行失败补偿，又不会提前引入现金支付规则。

### 方式二：提前建立通用订单

这会迫使阶段 2 同时决定会员折扣、优惠券、支付状态和现金价格快照，实际进入阶段 3 范围，因此没有采用。

### 方式三：只有积分流水，没有兑换单

这种方式虽然代码少，但用户无法通过稳定兑换单号查询商品、数量、价格快照和补偿状态，也无法可靠关联库存预占，因此没有采用。

## 3. V10 计划建立什么

V10 计划新增三张表：

```text
points_account            每个用户一个积分账户
points_ledger             不可修改的积分流水
points_redemption_order   积分专用兑换单和商品快照
```

同时扩展阶段 1 的库存状态：

```text
inventory_reservation: REVERSED
inventory_ledger:      RETURN
```

这些扩展不会修改 V9 文件，而是在 V10 中通过新的 `ALTER TABLE` 完成。V1～V9 继续保持不可修改。

新增权限规划：

```text
points:read
points:redeem
points:adjust
```

普通 USER 和 ADMIN 可以查询本人积分、创建积分兑换；只有 ADMIN 可以调整积分和冲正兑换。

## 4. 什么是不可变积分流水

假设用户有 5000 积分，兑换商品花费 3000：

```text
兑换前余额：5000
REDEMPTION 流水：DEBIT 3000
兑换后余额：2000
```

如果后续业务失败，系统不能删除或修改这条扣减流水，而是增加一条反向流水：

```text
原 REDEMPTION 流水：DEBIT 3000，保留不动
新 REVERSAL 流水：CREDIT 3000，关联原流水
冲正后余额：5000
```

这样可以回答：积分为什么减少、为什么又恢复、由哪个业务触发，避免账本历史被覆盖。

## 5. 幂等编号怎么使用

积分流水的唯一身份为：

```text
business_type + business_id
```

例如：

```text
business_type = REDEMPTION
business_id   = RDM-20260808-0001
```

客户端因为网络超时重复提交 20 次，系统只能扣一次积分。如果同一个编号换成另一个用户或不同积分数量，则返回幂等参数冲突。

兑换单号同时作为库存预占号：

```text
redemptionNo = RDM-20260808-0001
reservationNo = RDM-20260808-0001
channelCode = POINTS
```

这样积分流水、兑换单和库存记录可以通过一个稳定编号对应起来。

## 6. 兑换事务顺序

计划固定使用下面的顺序：

```text
读取可兑换 SKU 快照
  -> 计算 pointsPrice × quantity
  -> 抢占 PROCESSING 兑换单号
  -> 预占 POINTS 渠道库存
  -> 条件扣减积分
  -> 确认库存消费
  -> 兑换单变为 COMPLETED
```

这些操作都使用同一个 MySQL 本地事务。

例如用户有 2000 积分却兑换 3000 积分商品：

```text
积分条件扣减失败
-> 整个事务回滚
-> 不留下兑换单
-> 不留下扣分流水
-> 库存预占和库存流水也一起回滚
```

同理，库存不足时也不会扣除积分。

## 7. 为什么还要支持已确认库存反向恢复

兑换创建成功后库存已经从 `reservedStock` 进入 `consumedStock`。如果后续履约确认商品无效，仅仅返还积分还不够，商品库存也需要恢复。

计划新增：

```text
CONFIRMED -> REVERSED
```

库存变化：

```text
consumedStock - quantity
availableStock + quantity
```

并写入：

```text
RETURN:{redemptionNo}
```

它与普通取消不同：

- `RELEASED`：预占后、确认前取消；
- `REVERSED`：已经确认消费后，由补偿流程恢复。

## 8. 计划中的 8 个任务

### 任务 1：V10 数据库

创建积分账户、流水、兑换单、权限和库存反向状态，并验证空库迁移。

### 任务 2：积分领域契约

定义实体、枚举、错误码、DTO、VO、Mapper 和权限常量。

### 任务 3：积分账户服务

实现幂等加分、条件扣分、管理员调整和反向冲正。

### 任务 4：积分并发安全

验证 40 个并发请求争抢 17 积分时只能成功 17 个，并验证 20 次相同请求只扣一次。

### 任务 5：已确认库存反向恢复

为积分兑换失败提供 `CONFIRMED -> REVERSED` 的安全库存补偿。

### 任务 6：积分兑换事务

把商品快照、积分账户、积分流水和 `POINTS` 库存组合成一个原子兑换流程。

### 任务 7：用户和管理员 API

开放余额、流水、兑换创建/查询、管理员调整和管理员冲正接口。

### 任务 8：阶段验收

编写 API 文档，从空数据库迁移 V1～V10，运行聚焦测试、全量回归、打包和资产安全审查，再切换到阶段 3 规划。

## 9. 计划开放的接口

用户端：

```text
GET  /api/points/account
GET  /api/points/ledgers
POST /api/points/redemptions
GET  /api/points/redemptions
GET  /api/points/redemptions/{redemptionNo}
```

管理员：

```text
POST /api/admin/points/adjustments
POST /api/admin/points/redemptions/{redemptionNo}/reverse
```

用户接口不接收 `userId`，而是从 JWT 登录上下文获得当前用户，因此普通用户没有机会通过修改参数读取他人积分。

## 10. 明确不做什么

阶段 2 计划不包含：

- 优惠券；
- 会员折扣；
- 现金订单；
- 模拟支付；
- 积分加现金混合支付；
- 购物车；
- 抽奖发积分；
- 外部积分供应商；
- 地址和物流；
- Outbox、DLQ 或履约任务。

这些内容继续留在阶段 3～6，不能在执行阶段 2 时顺手加入。
