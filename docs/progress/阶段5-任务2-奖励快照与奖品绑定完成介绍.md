# 阶段 5 · 任务 2：奖励快照与奖品绑定

## 为什么需要这一层

抽奖奖品以前只知道“这是优惠券”或“这是积分”，并不知道具体发哪张券、发多少积分。任务 2 把“展示用的奖品”和“真正可履约的奖励定义”绑定起来，并在进入抽奖前生成不可变快照。

这样即使管理员后来修改了商品名或会员产品，已经发生的中奖仍可按照当时的内容核对和发放。

## 具体完成了什么

1. 建立五种类型明确的奖励载荷：商品、优惠券、积分、会员和额外抽奖次数。
2. 新增统一的 `RewardSnapshot`，记录奖励定义 ID、类型、目标、数量、JSON 载荷和 SHA-256 指纹。
3. 抽奖资格加载时批量读取奖励定义及其目标，避免逐个奖品反复查询。
4. 新建奖品必须绑定一个已启用且类型匹配的奖励定义。
5. 旧奖品允许保持未绑定，也允许首次补绑；一旦绑定，更新时不能换绑，省略绑定参数也不会解绑。
6. 优惠券、会员和商品目标必须存在且启用；离散奖励一次最多 100 份，积分仍支持大额长整数。
7. 配置中的整数溢出会转换成稳定的业务错误，不会泄漏底层 `ArithmeticException`。
8. 为旧履约路由补充了抽奖次数兼容处理器；后续新奖励流程会使用独立的抽奖次数账户，而旧路由仍能完整启动。

## 为什么优惠券同时保存模板 ID 和模板编码

- 模板 ID 适合数据库精确关联，例如 `templateId=12`。
- 模板编码适合人工排查和跨系统沟通，例如 `templateCode=WELCOME`。

只存 ID 时，日志里看到“12”很难判断是什么券；只存编码时，又不适合作为数据库内部关联。两者一起冻结在快照中，既方便机器处理，也方便人理解。

示例快照：

```json
{
  "templateId": 12,
  "templateCode": "WELCOME",
  "quantity": 2
}
```

它表示：中奖者应获得 2 张模板 ID 为 12、业务编码为 `WELCOME` 的优惠券。

## 新旧奖品如何共存

新奖品示例：

```text
奖品：500 积分
rewardDefinitionId：81
快照：{"points":500,"reason":"抽奖奖励"}
后续：走阶段 5 的统一奖励履约流程
```

旧奖品示例：

```text
奖品：历史咖啡券
rewardDefinitionId：null
快照：null
后续：继续走原有 BenefitFulfillmentRouter，不强制迁移旧数据
```

这种双轨方式避免一次性改坏历史奖品，同时保证从现在开始创建的奖品都具备真实发放所需的信息。
