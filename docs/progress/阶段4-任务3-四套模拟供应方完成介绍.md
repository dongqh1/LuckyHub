# 阶段 4 任务 3：四套模拟供应方完成介绍

## 为什么有这个

现在还没有接入某一家真实券、积分、会员或快递公司的账号和沙箱，但履约引擎必须能够真实运行和测试。只返回固定成功的假接口无法验证重复请求、网络超时和供应方已处理但响应丢失等生产问题，因此需要“行为像真实供应方”的本地模拟器。

## 这是干什么的

四个模拟器分别实现任务 2 的四个 Gateway。每套模拟器拥有独立记录表，平台履约任务和供应方记录也完全分开。这样能验证：平台认为未知时，供应方那边是否其实已经有一条成功记录。

## 具体实现

- 优惠券、积分、会员、物流各有一个 Spring `@Service` 适配器和独立数据表。
- 请求先序列化为稳定 JSON，再计算 SHA-256 指纹。同一 `fulfillmentNo` 与同一指纹重复提交返回原结果；同编号不同参数返回永久冲突。
- 数据库唯一键是并发下最后一道幂等防线，20 个线程同时提交也只产生一条供应方记录。
- 外部流水号按类型生成 `SIM-C-*`、`SIM-P-*`、`SIM-M-*`、`SIM-L-*`。
- 故障规则支持 `SUCCESS`、`RETRYABLE`、`PERMANENT`、`UNKNOWN_BEFORE`、`UNKNOWN_AFTER_SUCCESS`，规则消费使用事务和行锁，次数不会被并发重复消费。
- 错误只返回固定安全摘要，不保存堆栈、密钥或完整收件信息。

## 举例解释

优惠券：编号 `FUL-001` 第一次发放后生成一条 `sim_coupon_record`。客户端超时又提交相同请求时，会得到同一个外部流水号，不会再发第二张券；如果把券模板从 `NEW20` 改成 `NEW50` 还复用该编号，则返回参数冲突。

积分：把规则设成 `RETRYABLE` 1 次，第一次调用返回“暂时繁忙”且没有积分记录，下一次恢复成功。

会员：把规则设成 `UNKNOWN_AFTER_SUCCESS`，执行接口返回“结果未知”，但 `sim_membership_record` 已有成功记录；随后按履约编号查询可得到成功。这模拟了供应方成功后网络断线的真实场景。

物流：输入只保存 `李*`、`139****1234`、`上海市浦东新区***` 这类脱敏快照，并生成一个模拟物流受理号；阶段 6 才会引入真实地址和运单轨迹。

## 测试证据

- 红灯：测试最初因模拟器类型不存在而编译失败。
- 调试证据：先修复 SQL 文本块语法，再按项目 Spring Boot 4 的现有方式使用 `tools.jackson`，避免错误依赖旧 Jackson Bean。
- 绿灯：`SimulatorGatewayTests,SimulatorConcurrencyTests` 共 5 个测试全部通过，覆盖四类成功/查询、幂等冲突、四种失败行为和 20 线程并发。

当前模拟器可直接运行，也可在未来逐个被真实供应方适配器替换。
