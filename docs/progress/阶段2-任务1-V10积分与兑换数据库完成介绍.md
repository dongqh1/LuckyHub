# 阶段 2 · 任务 1：V10 积分与兑换数据库完成介绍

## 1. 这一步完成了什么

本任务为积分商城建立了数据库底座，新增：

- `points_account`：保存用户当前可用积分；
- `points_ledger`：保存每一次积分增加、扣减和冲正历史；
- `points_redemption_order`：保存一次积分兑换的商品快照和处理状态；
- `points:read`、`points:redeem`、`points:adjust` 三项权限；
- 库存“已确认后反向恢复”所需的 `REVERSED` 状态和 `RETURN` 流水操作。

这一步只完成数据库结构和迁移契约。积分增减服务、并发控制、兑换事务和 HTTP API 将在后续任务实现。

## 2. 三张新表分别负责什么

### 2.1 `points_account`：当前余额

每个用户最多只有一个积分账户，`user_id` 有唯一索引。`balance` 使用有符号 `BIGINT`，但数据库 CHECK 约束要求余额不能小于 0。

例如：

```text
用户 1001 当前余额：5000 分
points_account.balance = 5000
```

`version` 字段为后续并发更新保留，真正的安全扣减还会使用条件 SQL，避免多个请求把余额扣成负数。

### 2.2 `points_ledger`：不可变积分流水

余额回答“现在有多少积分”，流水回答“为什么变成这些积分”。每一笔流水记录：

- 用户；
- 业务类型和业务编号；
- 增加 `CREDIT` 或扣减 `DEBIT`；
- 本次变化数量；
- 变化后的余额；
- 被冲正的原流水；
- 备注和发生时间。

数据库使用 `business_type + business_id` 作为唯一业务身份。比如：

```text
business_type = REDEMPTION
business_id   = REDEEM-20260808-001
```

同一个兑换请求即使因为网络超时重复提交，也不能产生第二条扣减流水。

`reversal_of_ledger_id` 也是唯一的，表示同一笔原始扣减最多只能被冲正一次。

### 2.3 `points_redemption_order`：兑换过程和商品快照

兑换单保存：

- 兑换单号、用户、SKU 和数量；
- 单件积分价和总积分；
- 商品编码、名称、SKU 名称、类型和图片快照；
- `PROCESSING`、`COMPLETED`、`REVERSED` 状态；
- 冲正单号和失败原因。

保存快照的意义是：用户兑换后，即使管理员后来修改商品名称、图片或积分价格，历史兑换单仍展示当时真实成交的信息。

## 3. 为什么冲正要增加历史，而不是修改历史

假设用户原有 5000 分，用 3000 分兑换一个商品：

```text
初始余额：5000
REDEMPTION 扣减：-3000
扣减后余额：2000
```

如果后来因为商品无法履约需要返还积分，系统不会删除或修改上面的扣减流水，而是新增一条冲正流水：

```text
REVERSAL 增加：+3000
冲正后余额：5000
reversal_of_ledger_id -> 原 REDEMPTION 流水
```

这样可以同时看见“当时确实发生过兑换”和“后来为什么退回积分”，便于对账、审计和排查问题。

## 4. V10 对库存约束做了什么

V9 的库存预占结束状态原来只有：

```text
RESERVED -> CONFIRMED
RESERVED -> RELEASED
```

积分兑换在确认库存后，仍可能因为后续履约失败而需要完整补偿，因此 V10 扩展为：

```text
CONFIRMED -> REVERSED
```

对应的库存流水新增 `RETURN` 操作。它和 `RELEASE` 不同：

- `RELEASE`：预占还没确认，取消占用；
- `RETURN`：库存已经确认消费，后来再反向恢复。

V10 目前只放开数据库合法值，真正的原子状态转换会在 Task 5 实现。

## 5. 权限如何分配

| 角色 | 权限 | 用途 |
| --- | --- | --- |
| `USER` | `points:read` | 查询本人的积分、流水和兑换记录 |
| `USER` | `points:redeem` | 创建积分兑换 |
| `ADMIN` | `points:read` | 查询积分信息 |
| `ADMIN` | `points:redeem` | 创建积分兑换 |
| `ADMIN` | `points:adjust` | 人工调整积分和执行兑换冲正 |

普通用户没有 `points:adjust`，不能给自己加分，也不能自行冲正已完成兑换。

## 6. 数据库安全边界

V10 已用索引和 CHECK 约束保证：

- 一个用户最多一个积分账户；
- 积分余额和流水余额不能为负数；
- 每笔积分变化数量必须大于 0；
- 相同业务类型和业务编号不能重复记账；
- 同一笔扣减最多冲正一次；
- 兑换单号和冲正单号不能重复；
- 兑换数量、单价和总积分必须大于 0；
- 商品类型和兑换状态只能使用约定值。

本项目继续遵循现有数据库风格，不添加外键。用户、SKU 等关联有效性由后续服务在事务内验证，降低模块之间的数据库耦合。
