# 阶段 4 任务 2：Gateway 契约完成介绍

## 为什么有这个

真实券平台、积分中心、会员中心和物流公司提供的 API 格式都不一样，而且供应商未来可能更换。如果业务代码直接依赖某一家接口，更换时会牵动抽奖和商城主流程。Gateway 是平台与外部系统之间的一层稳定边界。

## 这是干什么的

四个 Gateway 分别只接收自己理解的强类型请求，并统一返回 `GatewayResult`。平台只认 `SUCCEEDED`、`RETRYABLE_FAILURE`、`PERMANENT_FAILURE`、`UNKNOWN` 和 `NOT_FOUND` 五种结果，不需要理解供应商的私有响应格式。

## 具体实现

- `CouponGateway` 接收券模板编码和数量。
- `PointsGateway` 接收积分数量和发放原因。
- `MembershipGateway` 接收会员产品编码和有效天数。
- `LogisticsGateway` 接收 SKU、数量及已经脱敏的收件人、手机和地区。
- 四个接口都有 `execute` 和按稳定履约编号查询的 `query`。
- 请求构造时完成必填、正数校验；物流信息未脱敏会直接拒绝。
- `GatewayResult` 会去除首尾空格、限制安全消息长度，并要求成功结果必须带外部流水号。

## 举例解释

当前模拟供应方和未来真实供应方都实现同一个接口。例如真实券系统返回 `code=200`，适配器把它翻译成 `SUCCEEDED`；若返回“系统繁忙”，翻译成 `RETRYABLE_FAILURE`。抽奖系统完全不用知道真实券系统的字段名。

物流示例只能传 `张*`、`138****5678`、`浙江省杭州市***`。如果误传 `张三` 和完整手机号，请求对象在进入数据库和供应方之前就会报错，降低隐私泄漏风险。

## 测试证据

- 红灯：`GatewayContractTests` 最初因 Gateway 包不存在而编译失败。
- 绿灯：4 个契约测试全部通过，覆盖四类请求、物流脱敏拒绝、结果归一化和接口方法签名。

下一任务会让四套本地模拟供应方分别实现这些接口；换成真实供应商时，只需增加新的实现。
