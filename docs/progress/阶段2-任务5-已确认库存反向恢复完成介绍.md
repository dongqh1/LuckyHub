# 阶段 2 · 任务 5：已确认库存反向恢复完成介绍

## 1. 这一步完成了什么

本任务为渠道库存增加了“确认后反向恢复”能力。原系统只能：

```text
RESERVED -> CONFIRMED
RESERVED -> RELEASED
```

现在新增：

```text
CONFIRMED -> REVERSED
```

并提供内部服务方法：

```java
ChannelInventoryView reverseConfirmed(String reservationNo);
```

它供下一步积分兑换编排在失败补偿时调用，当前不会直接暴露为 HTTP 接口。

## 2. 为什么确认后的库存还需要恢复

假设用户用 3000 积分兑换一件实物，兑换过程包含：

1. 预占 `POINTS` 渠道的一件商品；
2. 扣除用户 3000 积分；
3. 确认库存消耗；
4. 创建兑换订单和后续履约信息。

如果库存已经确认消耗，但后续数据库操作失败，系统必须同时把积分和商品库存补回。否则商品实际上没有成功兑换，后台库存却永久少一件。

本任务补齐了库存一侧的补偿动作。

## 3. 一个完整例子

`POINTS` 渠道原有 10 件可兑换商品：

```text
availableStock = 10
reservedStock = 0
consumedStock = 0
```

用户提交兑换后先预占 1 件：

```text
availableStock = 9
reservedStock = 1
consumedStock = 0
reservationStatus = RESERVED
```

确认消耗后：

```text
availableStock = 9
reservedStock = 0
consumedStock = 1
reservationStatus = CONFIRMED
```

如果 3000 积分兑换随后失败，调用：

```text
reverseConfirmed(兑换预占号)
```

得到：

```text
availableStock = 10
reservedStock = 0
consumedStock = 0
reservationStatus = REVERSED
```

也就是把已经算作“消费”的一件商品重新放回积分兑换渠道。

## 4. RELEASED 与 REVERSED 有什么区别

两者都会让商品重新可用，但发生的阶段不同：

```text
RELEASED：预占后还没有确认消费，取消占用
REVERSED：已经确认消费，后来因为业务失败执行反向恢复
```

对应库存变化为：

```text
RELEASED：reservedStock - quantity，availableStock + quantity
REVERSED：consumedStock - quantity，availableStock + quantity
```

不能把两者混在一起，否则审计时无法判断商品究竟是“从未消费”还是“消费后又补偿”。

## 5. 状态机保护

反向恢复只允许从 `CONFIRMED` 开始：

- `RESERVED -> REVERSED`：拒绝，返回 `46003`；
- `RELEASED -> REVERSED`：拒绝，返回 `46003`；
- `CONFIRMED -> REVERSED`：允许；
- `REVERSED -> REVERSED`：幂等返回相同结果；
- `REVERSED -> CONFIRMED`：拒绝，返回 `46003`；
- `REVERSED -> RELEASED`：拒绝，返回 `46003`。

原来的规则没有放宽：`confirm` 和 `release` 仍然只接受 `RESERVED`。

## 6. 数据库如何保证不会多恢复

服务使用 `READ_COMMITTED` 短事务依次完成：

```text
读取预占记录并要求状态为 CONFIRMED
-> 认领 RETURN:{reservationNo} 流水
-> 条件更新 CONFIRMED -> REVERSED
-> 条件减少 consumedStock 并增加 availableStock
-> 返回新库存视图
```

库存恢复 SQL 带有下限保护：

```sql
UPDATE inventory_channel_stock
SET consumed_stock = consumed_stock - :quantity,
    available_stock = available_stock + :quantity,
    version = version + 1
WHERE sku_id = :skuId
  AND channel_code = :channelCode
  AND consumed_stock >= :quantity;
```

如果数据库中的已消费数量异常不足，更新行数为 0，整个事务回滚，不会只改状态、不改库存。

`RETURN:{reservationNo}` 是本次恢复的唯一业务编号，因此相同请求重复到达只会存在一条 RETURN 流水。

## 7. 并发重复请求示例

测试让 20 个线程同时恢复同一个已确认预占：

```text
调用次数：20
实际库存恢复次数：1
RETURN 流水：1 条
最终 availableStock：10
最终 reservedStock：0
最终 consumedStock：0
最终状态：REVERSED
```

这覆盖了积分兑换服务超时重试、消息重复投递或多个补偿任务同时执行的情况。

- 抽奖并发。
