# 阶段 6 · 任务 7：物流管理与失败恢复

## 为什么管理员不能直接改状态

物流失败时，直接把数据库里的“失败”改成“已发货”会绕过履约任务的重试次数、隔离记录和幂等约束，可能重复叫快递，也可能把尚未成功的包裹展示成已发货。本任务给管理员提供安全入口：管理员表达“重试”或“终止”，系统仍交给原有履约状态机执行，再把结果投影回原发货单。这样不会另建任务，也不会改变物流身份。

## 做了什么

- 新增管理员发货单分页、详情、重试和终止接口，四个接口都严格要求 `shipping:operate`。
- 分页可按物流状态、来源类型、来源编号、目标用户和运单号筛选；列表与详情只返回脱敏姓名、手机号和地区，不返回地址密文、完整联系方式、密钥、签名、回调收据或供应商原始响应。
- `FAILED` 发货单且关联履约任务为 `QUARANTINED` 时，重试复用原履约任务，随后把发货单和抽奖权益恢复到处理中。
- 终止也复用原履约终止操作；处理中或已成功的履约任务，以及已发货、运输中、已签收、已终止的发货单，不能被强制终止。
- 人工备注采用允许型规则，只接受“人工核验通过”“确认可重试”“用户申请终止”等预定义安全运维短语及可选工单号，再截到 500 字。手机号、邮箱、身份证、固定电话、疑似完整地址、姓名/收件人标签、JSON、换行、控制字符和敏感关键词一律拒绝，错误响应也不会复述输入。操作者必须来自登录上下文，不接受请求体伪造。
- 投影器每轮只取履约任务 ID 升序的前 100 条，并原样按这条任务队列处理，不再按发货单 ID 重新排序。每张发货单先加锁，并通过独立事务处理；一条坏数据回滚不会拖垮后面的包裹。`DELIVERED` 和 `TERMINATED` 在入口和数据库条件更新处都有保护，旧的成功结果也不能让终止单“复活”为已发货。
- 权益物流进度覆盖 `CLAIMED -> FULFILLING -> SHIPPED -> DELIVERED`，以及隔离、重试恢复和终止。现金订单仍表示支付状态，积分兑换仍表示资产状态，物流号与物流状态作为单独可空字段追加。
- 权益、现金订单和积分兑换查询新增可空 `shippingNo`、`shippingStatus`。虚拟商品和历史无物流记录返回 `null`，原字段保持不变。

## 接口和状态

```http
GET  /api/admin/shipping/orders
GET  /api/admin/shipping/orders/{shippingNo}
POST /api/admin/shipping/orders/{shippingNo}/retry
POST /api/admin/shipping/orders/{shippingNo}/terminate
```

重试/终止请求可以带安全备注：

```json
{"note":"人工核验通过，确认可重试，工单 TASK-42"}
```

这里的备注不是自由粘贴框。管理员不能把“某收件人、完整手机号、某省某市某路某号”这类姓名、电话、地址复制进去；只记录为什么做这次运维动作，不记录包裹里的个人资料。

发货单主路径为 `READY -> FULFILLING -> SHIPPED -> IN_TRANSIT -> DELIVERED`；履约隔离会进入 `FAILED`，管理员重试后回到 `FULFILLING`。安全终止进入 `TERMINATED`，不会自动退款、退积分或退库存。

## 一个具体时间线：快递任务隔离后重试成功

1. 10:00，抽奖实物领取完成，权益为 `FULFILLING`，发货单 `SHIPPING-7` 和履约任务 `LOGISTICS-7` 已创建。
2. 10:03，模拟物流连续失败并超过次数，履约任务进入 `QUARANTINED`。投影器把发货单改为 `FAILED`，权益改为 `FULFILLMENT_FAILED`，只保存稳定错误码和安全短摘要。
3. 10:20，管理员修正非敏感商品资料，调用 `POST /api/admin/shipping/orders/SHIPPING-7/retry`，备注为“已核对商品资料”。系统没有新建任务，而是把原 `LOGISTICS-7` 恢复为可执行，并把发货单、权益恢复为 `FULFILLING`。
4. 10:21，原履约任务成功得到运单号，投影器把发货单和权益推进为 `SHIPPED`。后续签收回调在同一安全回调状态机中把二者推进为 `DELIVERED`。

再举两个边界例子：如果编号较大的发货单对应更早创建的履约任务，它仍先处理，因为排队依据是履约任务 ID，不是发货单 ID；如果管理员已经终止一张发货单，稍后才到达的旧“成功”投影会被入口和条件更新同时挡住，终止单绝不会重新显示为已发货。

## 边界与下一步

本任务没有接真实快递商，没有实现退款、退积分、退货、换货、购物车、多仓或运费计算，也没有修改 V1–V17。Task 8 将补充三种实物来源的端到端并发、幂等和隐私验收；Task 9 再整理阶段交付脚本和文档。

管理员列表组装脱敏快照目前仍是逐条查询，存在轻微 N+1 查询开销。本轮没有既有批量 Mapper 可直接复用，为避免扩大安全修复范围暂不改动；后续若列表规模或监控数据表明需要优化，应新增批量脱敏快照查询并保持同样的字段边界。
