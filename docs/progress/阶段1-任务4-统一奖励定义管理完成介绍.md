# 阶段 1 · 任务 4：统一奖励定义管理完成介绍

## 1. 这一步解决了什么问题

抽奖系统过去只能直接描述“奖品”，商城又会出现商品、积分、优惠券和会员等不同内容。如果每种奖励都写一套抽奖逻辑，后续会越来越难维护。

本任务新增了统一的“奖励定义”。抽奖活动以后只需要引用一条奖励定义，就能知道中奖后应该发什么、发多少，以及需要交给哪个后续系统处理。

可以把它理解成一张标准化的兑奖说明单：

- `rewardType`：奖励是什么类型；
- `targetId`：具体指向哪个商品 SKU、优惠券模板或会员方案；
- `quantity`：发放数量；
- `configSnapshot`：创建奖励时保存的额外配置快照。

## 2. 已完成的功能

### 2.1 支持五种奖励类型

| 类型 | 含义 | `targetId` 规则 | 示例 |
| --- | --- | --- | --- |
| `PRODUCT` | 商品或实物 | 必须填写，并指向一个已启用的商品 SKU | 抽中 1 台空气炸锅 |
| `COUPON` | 优惠券 | 必须填写，未来指向优惠券模板 | 抽中 1 张满 100 减 20 券 |
| `POINTS` | 积分 | 必须为空，数量直接写在 `quantity` | 抽中 500 积分 |
| `MEMBERSHIP` | 会员权益 | 必须填写，未来指向会员方案 | 抽中 1 个月黄金会员 |
| `DRAW_CHANCE` | 额外抽奖次数 | 必须为空，数量直接写在 `quantity` | 抽中 3 次额外抽奖机会 |

### 2.2 奖励配置校验

系统会拒绝以下错误配置：

- 商品奖励没有选择 SKU；
- 商品奖励选择了不存在或已禁用的 SKU；
- 优惠券或会员奖励没有填写目标；
- 积分或抽奖次数错误地填写了目标 ID；
- 奖励数量小于等于 0；
- 扩展配置不是合法 JSON；
- 奖励编码与已有记录重复。

奖励编码会自动去掉首尾空格，并通过数据库唯一约束保证不会重复。JSON 配置也会被标准化，例如：

```json
{ "source" : "lottery" }
```

保存后会统一为：

```json
{"source":"lottery"}
```

## 3. 管理接口

接口都需要管理员登录，并具有 `reward:manage` 权限。

### 3.1 创建奖励定义

```http
POST /api/admin/reward-definitions
Authorization: Bearer <管理员令牌>
Content-Type: application/json
```

创建“500 积分”奖励：

```json
{
  "rewardCode": "POINTS-500",
  "rewardName": "500积分",
  "rewardType": "POINTS",
  "targetId": null,
  "quantity": 500,
  "configSnapshot": "{\"source\":\"lottery\"}"
}
```

创建“一件实物商品”奖励：

```json
{
  "rewardCode": "PRODUCT-AIR-FRYER",
  "rewardName": "空气炸锅",
  "rewardType": "PRODUCT",
  "targetId": 10086,
  "quantity": 1,
  "configSnapshot": null
}
```

这里的 `10086` 不是商品名称，而是商品管理中已经创建并启用的 SKU ID。这样同一种商品的不同规格可以分别作为奖励。

### 3.2 查询奖励定义

```http
GET /api/admin/reward-definitions/{id}
Authorization: Bearer <管理员令牌>
```

返回内容包含奖励编码、名称、类型、目标、数量、配置快照、启用状态和创建更新时间。

## 4. 稳定错误码

| 错误码 | 含义 | HTTP 状态 |
| --- | --- | --- |
| `45001` | 奖励定义不存在 | 404 |
| `45002` | 奖励编码已存在 | 409 |
| `45003` | 奖励目标不合法 | 400 |
| `45004` | 奖励配置不合法 | 400 |

数据库的原始 SQL 错误不会直接返回给前端。

## 5. 举一个完整的理解例子

假设运营要创建一个奖池：

1. 一等奖：空气炸锅 1 台；
2. 二等奖：500 积分；
3. 三等奖：7 天会员；
4. 安慰奖：再抽 1 次。

现在可以先建立四条独立奖励定义：

- `PRODUCT / targetId=空气炸锅SKU / quantity=1`；
- `POINTS / targetId=null / quantity=500`；
- `MEMBERSHIP / targetId=7天会员方案 / quantity=1`；
- `DRAW_CHANCE / targetId=null / quantity=1`。

后续任务只需要把这些定义关联到抽奖奖品，再由统一履约流程根据类型调用积分、会员、商品库存或抽奖次数系统。抽奖算法本身不需要理解每一种奖励的内部细节。

## 6. 当前边界

本任务完成的是“定义和管理奖励”，尚未完成真正的奖励发放：

- 不会立即增加用户积分；
- 不会立即生成用户优惠券；
- 不会立即开通会员；
- 不会立即扣减或预占商品库存；
- 尚未把奖励定义绑定到现有抽奖活动。

这些能力会在后续积分、优惠券、会员、渠道库存和统一履约阶段逐步接入。本阶段保留 `COUPON`、`MEMBERSHIP` 的目标 ID，是为了让后续系统可以直接对接，不需要再次修改统一奖励的数据结构。
