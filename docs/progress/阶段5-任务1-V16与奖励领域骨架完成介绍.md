# 阶段 5 任务 1：V16 与奖励领域骨架完成介绍

## 为什么需要这个任务

阶段 4 只能记录“给某个用户发券、积分、会员或物流”的统一履约任务，但原抽奖记录只知道旧奖品类型，不知道它绑定的统一奖励、数量和发放快照。同时，额外抽奖次数没有账户，错误奖励事件也没有独立隔离位置。

V16 先建立稳定的数据地基，后续任务才能在不修改历史迁移的前提下实现统一奖励。

## 具体完成了什么

- 新增 `V16__integrate_lottery_rewards.sql`，V1-V15 保持不变。
- `lottery_draw_record` 和 `user_benefit` 增加奖励定义、类型、目标、数量、JSON payload 和 SHA-256 指纹字段。
- `user_benefit` 增加唯一且可空的 `fulfillment_no`，用来关联阶段 4 履约任务。
- 新增奖励抽奖次数账户、不可变流水和预留三张表。
- 新增 `lottery_reward_quarantine`，用于保存身份错配事件的安全原因和处置状态。
- 新增对应枚举、实体和 MyBatis Mapper。
- 全局数据库契约更新为 V16、43 张业务表，并让旧 V5 迁移守卫继续验证到最新版本。

## 为什么新字段允许为空

阶段 5 采用双轨兼容。历史奖品没有 `reward_definition_id`，也没有足够信息推断券模板、会员产品或 SKU，所以历史中奖记录的新字段必须允许为空。

新流程会一次性写全这些字段；旧流程仍然可以读取原来的 `prize_type` 和权益状态。

## 举例理解

旧积分奖可能仍是：

```text
prize_type = POINTS
reward_definition_id = null
reward_payload = null
```

阶段 5 新积分奖将保存：

```text
prize_type = POINTS
reward_definition_id = 21
reward_type = POINTS
reward_quantity = 500
reward_payload = {"points":500,"reason":"抽奖奖励"}
reward_fingerprint = 64 位 SHA-256 十六进制字符串
```

之后即使管理员调整奖励定义，已经中奖的用户仍按中奖瞬间保存的 500 积分处理。

抽奖次数预留例子：用户有 2 次可用奖励次数，开始一次抽奖后，账户会暂时变为：

```text
available_balance = 1
reserved_balance = 1
reservation.status = RESERVED
```

抽奖成功后预留次数才正式消费；抽奖失败则从预留余额退回可用余额。具体业务逻辑由后续任务实现，本任务先保证数据库能安全表达这些状态。
