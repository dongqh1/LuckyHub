# 阶段 5 · 任务 8：五类奖励端到端验收

## 为什么必须做完整端到端验证

单独验证抽奖、消息、履约或资产服务都通过，并不能证明它们连接后仍然正确。本任务从真实抽奖入口开始，让数据依次经过 MySQL 事务、Outbox、Redis Stream、奖励校验、模拟供应方和本地资产投影，最终检查用户真正得到的结果。

## 具体实现

1. 为优惠券、积分、会员、实物和抽奖次数分别创建启用的奖励定义与强制中奖活动。
2. 调用真实 `LotteryService.draw` 生成订单、中奖记录、权益、奖励快照和 Outbox 事件。
3. 通过真实 Redis Stream 发布与消费履约事件，不绕过消息协议。
4. 券、积分和会员运行统一履约 Worker，确认对应模拟供应方记录成功。
5. 运行资产投影，确认本地用户券、积分流水/余额和会员发放记录可用。
6. 实物确认没有物流模拟记录，只进入 `CLAIM_PENDING`。
7. 抽奖次数确认直接进入次数账户和不可变流水。
8. 对同一事件和投影再次执行，确认所有记录数量不增加。
9. 权益查询追加奖励定义、奖励类型、奖励数量、履约编号和履约状态；旧权益这些字段保持 `null`。
10. 修复 MySQL `REPEATABLE READ` 下并发消息的旧快照问题：先锁定权益身份，再读取消费记录，八线程重复投递只创建一条履约任务和一条消费记录。

```text
优惠券 x2
抽奖 -> 履约任务 -> sim_coupon_record 1 条
     -> coupon_issue_record 2 条 -> user_coupon 2 张 -> AVAILABLE

积分 300
抽奖 -> 履约任务 -> sim_points_record 1 条
     -> points_ledger 1 条 -> balance +300 -> AVAILABLE

会员 x2
抽奖 -> 履约任务 -> sim_membership_record 1 条
     -> membership_grant_record 2 条 -> 有效期累计 -> AVAILABLE

实物 x1
抽奖 -> CLAIM_PENDING
     -> sim_logistics_record 0 条

抽奖次数 x3
抽奖 -> draw_chance_ledger 1 条 -> available_balance +3 -> AVAILABLE
```
