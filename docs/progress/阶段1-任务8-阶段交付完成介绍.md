## 3. 为什么要从空数据库再验证一次

在已经运行过的开发数据库中测试，只能证明“当前数据库最终结构可用”，不能完全证明一个新环境能从 V1 顺利升级到 V9。

本任务创建临时数据库：

```text
luckyhub_phase1_verify
```

Flyway 日志确认：

```text
Empty Schema
  -> V1
  -> V2
  -> V3
  -> V4
  -> V5
  -> V6
  -> V7
  -> V8
  -> V9
```

最终 9 个迁移全部应用成功，14 个迁移契约测试通过。验收结束后，临时数据库和临时授权都已删除，原开发数据库没有被清空。

第一次尝试时，临时库虽然创建成功，但应用账号没有新库权限，因此连接阶段就被 MySQL 拒绝，Flyway 还没有执行。确认根因后，只给临时库增加临时授权再重试，迁移成功后立即撤销授权并删除临时库。

这个例子说明：

```text
数据库连接失败 ≠ 迁移脚本失败
```

必须先看错误发生在连接、校验还是具体迁移 SQL，才能判断真正问题。

## 5. 代码审查结论

### 5.1 库存会不会变成负数

不会。预占、确认和释放都使用带余额条件的单条 SQL。

例如预占 3 件必须满足：

```text
available_stock >= 3
```

不满足时 SQL 更新 0 行并返回库存不足，不会先减成负数再回滚。

### 5.2 不同渠道会不会分配超过总库存

不会。每次分配都要求：

```text
total_stock - allocated_stock >= 本次分配数量
```

这个条件直接在数据库更新语句中判断，并发请求不能一起越过同一个余额。

### 5.3 相同业务号能否偷换 SKU 或数量

不能。幂等流水会记录：

```text
businessNo + skuId + channelCode + operation + quantity
```

编号已存在时必须逐项一致，任何一项不同都会返回 `46004`。

### 5.4 新功能有没有改变旧抽奖

没有。阶段 1 起点之后没有修改 `lottery`、`activity` 或 `benefit` 主业务代码，也没有让新渠道库存替换旧活动奖品库存。

`marketing_prize` 只增加一个可空的 `reward_definition_id`，当前抽奖不读取它。

### 5.5 用户能否看到精确库存

不能。用户商品响应 `ProductView/SkuView` 没有库存字段。库存数据只通过要求 `inventory:manage` 的管理员接口返回。

### 5.6 数据库错误会不会直接暴露

正常业务重复键会转成稳定业务错误码。其他数据库异常由全局异常处理器转换为安全的系统错误，不会把原始 SQL、表名或堆栈作为 API 消息返回。

### 5.7 旧迁移是否被修改

以阶段 1 起点 `18b6ad8` 为基准比较，V1～V7 没有变化。本阶段只增加 V8 和 V9。

最终审查：
