# 阶段 6 · 任务 4：抽奖实物领取与超时

## 为什么需要本任务

阶段 5 的实物中奖只停在 `CLAIM_PENDING`。这是有意保留的安全边界：中奖时用户尚未选择地址，系统不应提前冻结地址、创建发货单或物流任务。本任务补齐“期限内领取”和“超时归还奖池库存”两条互斥路径。

## 实现

商品奖励进入可领取状态时，在同一个条件更新中冻结 `claim_deadline = now + luckyhub.shipping.claim-period`。领取接口为：

```http
POST /api/benefits/{benefitId}/claim
Content-Type: application/json

{
  "requestId": "3eb67b1c-92c3-4a41-a652-dc815c23b56e",
  "addressId": 18
}
```

领取事务先 `FOR UPDATE` 锁定 `user_benefit`，再验证用户、实物类型、状态、严格截止时间以及 draw record 与 benefit 中冻结的 PRODUCT 奖励身份、SKU 和数量。随后创建 `LOTTERY_BENEFIT` 地址快照，调用统一 `ShippingOrderService` 创建唯一发货单和 `LOGISTICS-{shippingOrderId}` 任务，最后把发货单绑定到权益并推进为 `FULFILLING`。任一步失败都会回滚快照、发货单、任务和权益更新。

UUID 请求号会规范化为小写。相同请求号、相同地址和相同业务身份重复提交返回原发货单；地址、来源或商品身份变化会返回幂等冲突，且不会覆盖第一次的不可变快照。

重复领取还会交叉核对 `user_benefit.shipping_order_id == shipping_order.id`，并要求权益已处于 `CLAIMED`、`FULFILLING`、`SHIPPED`、`DELIVERED`、`FULFILLMENT_FAILED` 或 `FULFILLMENT_TERMINATED`。因此，即使数据库中意外出现“同一来源有发货单、权益却没有绑定它”的残缺数据，也不会被误认成一次成功的幂等重试。合法重试先识别原发货单，不会因为原领取期限后来已过而失败。

超时任务按配置的 interval、initial delay 和 batch size 扫描。外层扫描不持有整批事务，而是通过 `id > afterId` 的游标分页继续前进；每个权益由独立 `REQUIRES_NEW` 事务处理。它同样先锁权益，再根据 V17 实际存在的冻结 `draw_record.activity_id + prize_id` 唯一解析 `marketing_activity_prize`；V17 没有 `activity_prize_id`，因此没有修改旧迁移。库存流水固定使用 `CLAIM-EXPIRE-{benefitId}`、操作 `CLAIM_RETURN`，流水唯一约束保证只回补一次。流水、奖品库存加一和 `CLAIM_EXPIRED` 状态处于同一个单权益事务，补偿失败则该权益全部回滚，但调度器仍会处理本页和后续页的其他权益。

例如批次成功上限是 1，最早的 50 条权益都因冻结身份损坏而失败，第 51 条正常：游标会跳过这 50 条失败候选并让第 51 条成功过期；坏数据不会长期占住 `limit=1`，也不会回滚第 51 条的库存补偿。

## 同时领取与超时的例子

假设用户在截止瞬间点击领取，同时调度器也扫描到该权益。两方都会竞争同一行锁：

- 用户先获得锁：地址快照、发货单和物流任务提交，权益成为 `FULFILLING`；调度器随后看到它已不再是 `CLAIM_PENDING`，不回补库存。
- 调度器先获得锁：库存流水与回补提交，权益成为 `CLAIM_EXPIRED`；用户随后不能领取，也不会创建任何物流数据。

因此不存在“既发货又回补库存”的第三种结果。在 `now == claim_deadline` 时领取严格视为过期。

## 测试与边界

测试覆盖领取成功、越权与非实物拒绝、截止时间相等、UUID 校验、相同请求幂等、地址/请求号/冻结身份冲突、权益与发货单绑定和状态校验、20 线程并发只产生一个快照/发货单/物流任务、领取与超时竞争、领取失败的全事务回滚、补偿失败时流水/库存/权益的全事务回滚、跨页毒数据不饥饿，以及 V17 对旧 `CLAIM_PENDING` 数据提供部署后 7 天宽限期。测试数据使用随机业务标识和定向清理，不依赖全局表数量。

本任务不实现物流回调、轨迹、管理员重试、退款、退货或售后；中奖时仍不创建物流数据。下一步任务 6 将实现模拟物流事件、签名回调和单调轨迹推进。
