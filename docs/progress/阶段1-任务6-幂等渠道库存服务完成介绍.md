# 阶段 1 · 任务 6：幂等渠道库存服务完成介绍

## 1. 这一步解决了什么问题

Task 5 只建立了库存数据表，本任务让这些表真正具备可调用的库存行为：

- 初始化一个 SKU 的总库存；
- 把总库存分配给商城、积分商城等业务渠道；
- 在用户下单或中奖时预占库存；
- 业务成功后确认消费；
- 业务取消后释放库存；
- 查询一个 SKU 在指定渠道的实时库存状态。

库存服务面对的核心问题不只是“做加减法”，还包括高并发和网络重试。系统必须保证库存不会变成负数，同一个请求无论重试多少次都只能产生一次效果。

## 2. 已实现的操作

### 2.1 初始化 SKU 总库存

输入：

```text
skuId = 10086
totalStock = 20
businessNo = INIT-10086
```

结果：

```text
总库存 = 20
已分配 = 0
```

只有存在且已启用的 SKU 才能初始化库存。

### 2.2 向渠道分配库存

输入：

```text
skuId = 10086
channelCode = mall
quantity = 10
businessNo = ALLOC-10086-MALL-1
```

渠道编码会自动去掉首尾空格并转成大写，因此 `mall`、` MALL ` 最终都表示 `MALL`。

结果：

```text
SKU 总库存 = 20
总计已分配 = 10
MALL 分配库存 = 10
MALL 可用库存 = 10
```

条件更新保证所有渠道的分配总量不能超过 SKU 总库存。

### 2.3 预占库存

预占会把库存从 `availableStock` 原子地移动到 `reservedStock`：

```text
预占前：available=10, reserved=0, consumed=0
预占 3 件
预占后：available=7, reserved=3, consumed=0
```

预占单号会生成固定流水号：

```text
RESERVE:{reservationNo}
```

### 2.4 确认库存

业务成功后，确认操作把库存从预占转为已消费：

```text
确认前：available=7, reserved=3, consumed=0
确认 3 件
确认后：available=7, reserved=0, consumed=3
```

确认流水号：

```text
CONFIRM:{reservationNo}
```

已经确认的预占再次确认时直接返回当前状态，不会重复消费。

### 2.5 释放库存

如果订单取消、领奖超时或业务失败，释放操作把库存退回可用数量：

```text
释放前：available=7, reserved=3, consumed=0
释放 3 件
释放后：available=10, reserved=0, consumed=0
```

释放流水号：

```text
RELEASE:{reservationNo}
```

已经释放的预占再次释放时直接返回当前状态，不会重复增加库存。

## 3. 什么是幂等

幂等可以理解为：同一个业务请求执行一次和执行多次，最终效果相同。

例如客户端请求预占 1 件商品，但响应在网络中丢失。客户端不知道服务器是否成功，于是用相同预占号重试 20 次。

正确结果必须是：

```text
库存只减少 1 件
预占记录只有 1 条
RESERVE 流水只有 1 条
```

系统使用唯一业务号抢占处理权：

- 第一个请求成功建立库存流水并执行库存变化；
- 后续相同请求读取第一条请求的结果；
- 如果相同业务号换了 SKU、渠道、操作或数量，返回幂等参数冲突；
- 不会把不同参数错误地当成合法重试。

## 4. 并发库存为什么不会变成负数

库存判断和扣减在一条数据库 SQL 中完成，而不是先查询再扣减。

逻辑类似：

```sql
UPDATE inventory_channel_stock
SET available_stock = available_stock - 1,
    reserved_stock = reserved_stock + 1
WHERE available_stock >= 1;
```

数据库只允许满足条件的请求更新成功。

### 并发测试例子

测试准备：

```text
SKU 总库存 = 20
MALL 渠道库存 = 10
100 个请求同时各预占 1 件
```

实际验证结果：

```text
成功请求 = 10
库存不足请求 = 90
availableStock = 0
reservedStock = 10
consumedStock = 0
没有任何库存字段小于 0
```

另一项测试把完全相同的预占号同时发送 20 次，最终只生成一条预占记录、一条预占流水，并且只预占 1 件。

## 5. 预占状态机

允许的变化：

```text
RESERVED -> CONFIRMED
RESERVED -> RELEASED
```

禁止的变化：

```text
CONFIRMED -> RELEASED
RELEASED -> CONFIRMED
```

原因是已经正式消费的库存不能再退回，而已经退回的库存也不能再被确认为消费。这类错误会返回库存状态冲突。

## 6. 稳定错误码

| 错误码 | 含义 | 常见场景 |
| --- | --- | --- |
| `46001` | 库存不存在 | SKU 未初始化、渠道未分配、预占单不存在 |
| `46002` | 可用库存不足 | 分配超过总库存、预占超过渠道可用库存 |
| `46003` | 库存状态冲突 | 已确认后释放、已释放后确认、重复初始化 |
| `46004` | 库存幂等参数冲突 | 相同业务号使用了不同 SKU、渠道或数量 |
| `46005` | SKU 不可用于库存配置 | SKU 不存在或已禁用 |

原始数据库唯一键和 SQL 异常不会作为正常业务响应暴露。

## 7. 事务和并发策略

每个库存变化都在一个本地数据库事务中完成。流水、预占状态和库存数字要么一起提交，要么一起回滚。

库存事务使用 `READ_COMMITTED` 隔离级别。这样重复请求在等待首个事务完成后，可以读取已经提交的胜出记录进行身份校验，不需要让所有重试请求继续争夺写锁。

这次并发测试曾发现“重复请求重新加锁导致死锁”的问题，最终改为：

1. 原子尝试写入唯一业务流水；
2. 写入成功者执行库存变化；
3. 写入失败者等待胜出事务提交；
4. 普通读取胜出记录并校验请求参数；
5. 参数一致则返回当前状态，不一致则报告冲突。

## 8. 当前边界

本任务完成的是 Java 服务和数据库并发安全逻辑，还没有对外提供 HTTP 接口。Task 7 会增加管理员库存 API。

当前抽奖系统原有的 `ActivityPrizeInventoryService` 仍然独立运行。本任务没有修改旧抽奖库存表、扣减逻辑或抽奖事件，因此现有抽奖主链路不会自动使用新渠道库存。

后续统一抽奖履约阶段才会把 `LOTTERY:{activityId}` 渠道接入新库存服务。
