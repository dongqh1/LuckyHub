# 阶段6任务8：三来源端到端完成介绍

## 为什么还要一层验收

前七个任务分别证明了地址、快照、领取、发货、回调和管理功能，但“零件都能工作”不等于“整条业务链能工作”。本任务把抽奖、现金和积分放进同一组验收，证明它们通过各自规则后，都进入同一张发货单、同一个 `LOGISTICS` 任务和同一套签收流程。

## 三条时间线

1. 抽奖：公开抽奖服务创建实物权益，中奖时状态只是 `CLAIM_PENDING`，此时发货单数量为零。用户用随机 `requestId` 和自己的地址领取，系统冻结一份地址快照，创建唯一发货单和任务；worker 生成模拟运单，四个签名回调依次推进，projector 最终把权益和物流都变成 `DELIVERED`。
2. 现金：用户用公开下单服务选择地址，系统先冻结快照；模拟支付成功回调只创建一张发货单和一个任务。worker 和签名回调把物流推进到 `DELIVERED`，但现金订单仍用 `PAID` 表示支付结果，两个状态不会混成一个字段。
3. 积分：用户先有积分，再用公开兑换服务选择实物和地址。一次事务内扣积分、确认库存、冻结快照并创建物流。签收后兑换仍是 `COMPLETED`，物流另为 `DELIVERED`。

## 重复请求例子

把同一个支付回调、兑换号或领取 `requestId` 同时发 20 次，数据库仍只落一份不可变快照、一张发货单、一个稳定编号 `LOGISTICS-{shippingOrderId}` 的任务。20 个 worker 同时抢同一任务，也只生成一条安全模拟运单记录。重复回调由 callbackId、nonce 摘要和供应方事件身份共同挡住。

## 隐私例子

验收使用完整姓名“顾隐私”、完整手机和详细门牌作为探针，然后扫描发货、履约、尝试、隔离、轨迹、回调和模拟器的文本/JSON列，并捕获日志、响应和错误。完整值不会出现在这些位置；用户和管理员只看到 `顾*`、`139****4321` 和地区摘要。明文只允许在地址簿/快照的加密列对应的解密边界，以及 Gateway 调用前的瞬时内存中存在。

## 实现与测试

- `ShippingTestFixture` 用随机全局业务号创建用户、商品、奖励、活动、积分和地址，清理只按本次记录的用户、SKU、活动、发货单和履约号逐项执行，不使用用户名模糊匹配影响其他测试。
- `PhysicalShippingEndToEndTests` 覆盖三条真实时间线、四段有序轨迹、用户/管理员/来源分离查询。
- `PhysicalShippingConcurrencyTests` 覆盖重复支付、兑换、领取和 worker 并发。
- `PhysicalShippingSafetyTests` 扫描数据库文本/JSON、捕获日志，并序列化用户、管理员和来源响应做 PII/secret 检查。
- focused 与 Phase 6 focused 命令均通过 `scripts/Invoke-Maven.ps1` 在 JDK 17 下运行；随机临时 schema 的全量 `clean test` 在 finally 中撤权并只删除本次 schema。

验收测试首次运行现金链路直接通过，说明已有生产实现满足要求；积分与抽奖的最初失败分别来自测试类型和 fixture 商品模式配置，修正测试后通过，没有为迁就测试修改生产代码。

## Fixture 边界与下一步

商品、奖励、活动、地址、积分、现金订单、兑换和领取都走公开服务。抽奖 Outbox 的外部 Redis 传输已由阶段5覆盖；本验收读取公开抽奖事务生成的 Outbox payload，再调用正式消费服务，这是唯一没有重复搭建 Redis Stream 的 setup 边界。测试只用 SQL 做定向断言和定向清理，不直接修改业务状态。

下一步是阶段6任务9：空库迁移、全量回归、可执行 JAR、OpenAPI 冒烟和最终交接；本任务不扩展真实快递、运费、售后或退换货范围。
