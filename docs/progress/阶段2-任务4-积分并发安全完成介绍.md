# 阶段 2 · 任务 4：积分并发安全完成介绍

## 1. 这一步完成了什么

本任务使用真实 MySQL 和多线程同时调用 `PointsAccountService`，证明同一用户受到并发争抢时仍满足：

- 积分余额永远不会小于 0；
- 余额不足只返回业务错误，不泄漏数据库死锁异常；
- 成功扣减次数与生成的流水数一致；
- 相同业务编号的重复请求只扣一次积分；
- 所有重复调用者获得同一条积分流水；
- 同一个用户最终只有一个积分账户。

新增测试文件为 `PointsAccountConcurrencyTests`，同时修复了测试实际发现的账户锁升级死锁。

## 2. 示例一：40 个人同时争抢 17 积分

测试先给一个用户存入 17 积分，然后让 40 个线程同时发起不同业务编号的 1 积分兑换：

```text
初始余额：17
并发请求：40 个，每个扣 1 分
成功：17 个
余额不足：23 个
最终余额：0
兑换扣减流水：17 条
负数账户或负数流水快照：0 条
```

扣减依然由数据库条件更新完成：

```sql
UPDATE points_account
SET balance = balance - 1, version = version + 1
WHERE user_id = ? AND balance >= 1;
```

可以把它理解为 40 个人同时从一个盒子里拿硬币，而盒子里只有 17 枚。数据库逐个锁定同一账户行，只有前 17 个人能拿到硬币，后 23 个人看到余额不足。任何时刻都不会先拿成 `-1` 再补救。

## 3. 示例二：20 次重复请求只扣一次

测试再给一个用户存入 100 积分，让 20 个线程使用完全相同的业务编号同时扣 10 分：

```text
初始余额：100
请求次数：20
业务编号：全部为 CONCURRENT-SAME-DEBIT
最终余额：90
扣减流水：1 条
20 个调用结果中的流水 ID：全部相同
积分账户：1 个
```

这模拟了用户点击一次兑换，但客户端因超时、重试或消息重复投递而把同一请求送来 20 次。系统把 `business_type + business_id` 当作业务身份证，因此 20 次调用会收敛到第一次成功的结果，而不是扣成 0 分。

## 4. 并发测试发现并修复了什么

首次真实并发运行发现 `DeadlockLoserDataAccessException`。原因不是条件扣减本身，而是事务入口原来使用：

```sql
INSERT IGNORE INTO points_account (...);
```

账户已经存在时，多个事务可能先取得兼容锁，随后同时尝试把锁升级为余额更新需要的排他锁，形成死锁。

现在“确保账户存在”改为：

```sql
INSERT INTO points_account (...)
VALUES (...)
ON DUPLICATE KEY UPDATE user_id = ?;
```

重复键分支不会改变用户 ID，但会在事务入口取得该账户行的排他锁。于是同一用户的资产变化按统一顺序串行：

```text
锁定或创建账户
-> 查询相同业务流水
-> 条件修改余额
-> 写入积分流水
-> 提交事务
```

后续重复请求等前一个事务提交后再继续，能够在扣款前读到已有流水并直接返回。不同用户仍锁定各自的账户，不会被全局串行化。

## 5. 测试如何保证请求真的同时开始

测试使用固定大小线程池和两个 `CountDownLatch`：

1. 每个工作线程先报告“准备完成”；
2. 主线程确认所有线程都已就绪；
3. 主线程一次性打开开始栅栏；
4. 收集每个请求结果并直接查询数据库核对余额和流水。

每个测试还有 45 秒总超时、Future 30 秒等待上限和线程池关闭校验，死锁或线程泄漏不会被误判为成功。
