# LuckyHub 抽奖核心与迷你商城设计

> 日期：2026-08-08  
> 状态：待用户复核  
> 定位：以抽奖系统为核心，用最小可用商城承载商品、积分、优惠券、会员和实物物流的完整业务闭环。

## 1. 目标

在现有抽奖、库存、Outbox、Redis Stream 和权益查询能力之上，增加一个简化的虚拟商城。用户既可以抽奖获得奖励，也可以购买或用积分兑换商品；优惠券和会员在结算时产生优惠；实物商品进入领奖、发货和物流流程。

本阶段使用本地模拟支付、模拟券、模拟积分、模拟会员和模拟物流系统，不依赖真实第三方账号。所有外部能力都通过可替换适配器调用，未来接入真实平台时不修改抽奖核心和商城领域逻辑。

成功标准：

- 抽奖可发放实物、虚拟商品、优惠券、积分、会员和抽奖资格；
- 用户可现金模拟购买商品，也可使用积分全额兑换指定商品；
- 现金订单支持优惠券和会员折扣；
- 积分兑换订单不叠加现金券或会员价格折扣；
- 实物奖励和实物订单统一进入地址确认、发货、运输、签收流程；
- 所有发放、扣减和物流调用都具备稳定幂等号、重试记录、对账和人工处理入口；
- 现有抽奖接口和历史数据保持兼容。

## 2. 范围边界

### 2.1 本阶段包含

- 商品目录、SKU、现金售价、积分兑换价和上下架；
- 商品总库存与商城销售、积分兑换、抽奖活动三个渠道库存；
- 用户积分账户和不可变积分流水；
- 优惠券模板、用户券包、锁券、核销和释放；
- 会员产品、用户会员有效期和基础会员规则；
- 立即购买，不实现购物车；
- 模拟支付成功、失败和超时；
- 用户收货地址、订单地址快照、领奖截止时间；
- 履约任务、调用流水、重试、隔离队列和人工重试；
- 模拟物流下单、运单号、运输状态回调和主动查询；
- 管理端最小查询能力。

### 2.2 本阶段不包含

- 微信、支付宝或银行卡真实支付；
- 退款、退货、换货和售后工单；
- 购物车、拼团、秒杀、预售和复杂促销叠加；
- 积分提现或按人民币余额记账；
- 多商户、多仓库智能路由和真实运费计算；
- 前端页面；接口通过 Swagger/Postman 验证；
- 将 LuckyHub 拆成多个独立部署的微服务。

## 3. 总体架构

保持单体 Spring Boot 应用和 MySQL/Redis 基础设施，按业务包划分模块：

```text
lottery       抽奖编排、活动库存、中奖记录
catalog       商品、SKU、价格、上下架
inventory     总库存、渠道库存、预占和扣减
points        积分账户与积分流水
coupon        券模板、用户券、锁定和核销
membership    会员产品、有效期和规则
order         下单、价格快照、订单状态
payment       模拟支付
benefit       统一奖励和履约任务编排
shipping      地址、发货单、运单和物流状态
integration   券/积分/会员/物流适配器及模拟实现
```

领域服务只依赖 Gateway 接口，不依赖模拟实现或未来真实供应商 SDK。模拟系统作为同一应用中的独立包和独立数据表存在，通过 HTTP 测试适配器或进程内适配器验证超时、重复调用、结果未知和回调场景。

## 4. 核心业务模型

### 4.1 商品与 SKU

`product` 表示用户看到的商品，`product_sku` 表示可销售和计库存的具体规格。第一版允许每个商品只有一个默认 SKU，但数据库和接口保留一对多关系。

SKU 关键字段：

- `sku_code`：稳定业务编码；
- `fulfillment_type`：`PHYSICAL` 或 `VIRTUAL`；
- `cash_price_cent`：现金价格，单位分；
- `points_price`：积分兑换价；
- `cash_enabled`、`points_enabled`：允许的购买方式；
- `status`：上下架状态；
- `version`：乐观锁版本。

历史订单和中奖记录保存名称、图片、价格、规格等快照，不回读当前商品信息覆盖历史。

### 4.2 统一奖励定义

抽奖活动不直接把 `PrizeType` 当作最终履约规则，而是引用 `reward_definition`：

```text
PRODUCT       商品/SKU，可能是实物或虚拟商品
COUPON        指定优惠券模板
POINTS        固定数量积分
MEMBERSHIP    指定会员产品和时长
DRAW_CHANCE   固定次数的抽奖资格
```

奖励定义保存目标业务 ID、数量和版本化配置。抽奖中奖时创建奖励实例和履约任务，确保后续修改模板或商品不会改变已经中奖的内容。

现有 `marketing_prize` 和 `user_benefit` 保留，通过新字段逐步迁移；不修改已经发布的 V1-V7，所有结构变化从 V8 开始。

### 4.3 库存

采用“总库存 + 渠道库存”模型：

```text
总库存 100
├─ 商城销售 70
├─ 积分兑换 20
└─ 抽奖活动 10
```

渠道库存分配不能超过总库存。抽奖继续使用活动奖品库存；商城订单和积分兑换使用各自渠道库存。第一版不在渠道之间自动借库存，管理员显式调整分配。

库存动作必须以业务单号幂等：订单创建时预占，支付成功或兑换成功时确认，取消或超时时释放。中奖库存沿用现有 MySQL 条件扣减语义，不因新增商城而回退为弱一致实现。

## 5. 积分系统

积分是独立资产，不作为人民币余额，也不能提现。系统可以展示参考兑换价值，但计算只使用整数积分。

每个用户一个积分账户，余额由流水汇总约束：

```text
LOTTERY_REWARD     抽奖获得
ORDER_REWARD       消费返积分
MEMBERSHIP_BONUS   会员奖励
REDEMPTION         积分兑换扣减
REVERSAL           业务冲正
MANUAL_ADJUSTMENT  管理员调整
```

每笔流水使用唯一 `business_type + business_id` 防止重复入账。余额扣减使用条件更新，禁止负数。积分兑换下单时一次性扣减；后续失败只能写反向冲正流水，不能修改或删除原流水。

## 6. 优惠券系统

优惠券模板第一版支持：

- 无门槛固定金额券；
- 满额固定金额券；
- 适用全部商品或指定商品；
- 有效期和每人领取上限；
- 是否允许与会员折扣叠加。

用户券状态：

```text
AVAILABLE -> LOCKED -> USED
                \-> AVAILABLE  订单取消或支付超时释放
AVAILABLE -> EXPIRED
```

订单创建时锁券并保存优惠快照；支付成功后核销；取消或超时后释放。相同用户券不能同时被两个订单使用。优惠金额不得超过折后商品金额，订单最低支付金额为 0 分。

## 7. 会员系统

会员产品包括月卡、季卡和年卡。用户会员保存等级、开始时间和结束时间。重复获得相同等级会员时，从 `max(当前有效期, 当前时间)` 开始顺延，不覆盖剩余时间。

第一版会员权益仅实现：

- 商品统一折扣率；
- 每日额外抽奖次数；
- 消费积分倍率。

价格计算顺序固定为：

```text
商品原价
-> 会员折扣
-> 优惠券抵扣
-> 应付金额
```

订单保存每一步金额快照。积分兑换订单不应用会员价格折扣和现金优惠券，第一版也不为积分兑换返积分。

## 8. 订单与模拟支付

第一版只支持单 SKU 立即购买。订单类型：

```text
CASH_PURCHASE       现金模拟购买
POINTS_REDEMPTION   积分全额兑换
LOTTERY_REWARD      抽奖实物领奖生成的零元订单
```

现金订单状态：

```text
PENDING_PAYMENT -> PAID -> FULFILLING -> COMPLETED
        |            |
        v            v
    CANCELLED     FULFILLMENT_FAILED
```

积分兑换在创建时完成积分扣减和库存确认，然后进入 `PAID` 等价状态。抽奖实物中奖创建零元订单，用户确认地址后进入履约。

模拟支付使用稳定支付单号，支持成功、失败和处理中三种结果。支付回调必须验签模拟、幂等处理，并通过订单状态条件更新防止重复确认。

## 9. 实物领奖与物流

用户可以维护多个地址。订单必须保存收件人、手机号和完整地址快照，后续修改地址簿不影响历史订单。

抽中实物后的流程：

```text
中奖
-> 创建 CLAIM_PENDING 奖励和零元订单
-> 用户在截止时间前选择地址
-> 地址快照确认
-> 创建发货任务
-> 模拟物流返回运单号
-> SHIPPED
-> 模拟回调 IN_TRANSIT / DELIVERED
-> 订单 COMPLETED
```

超过领奖截止时间仍未提交地址，奖励进入 `CLAIM_EXPIRED`，库存是否回补通过活动规则固定配置；第一版默认回补到原抽奖活动渠道库存并记录库存流水。

收件人姓名、手机号和详细地址属于敏感信息：响应默认脱敏，日志禁止输出明文，数据库字段通过应用层加密保存，地址快照只有本人和具备物流管理权限的管理员可访问。

## 10. 统一履约底座

现有 handler 不直接执行远程调用。新增 `fulfillment_task` 和 `fulfillment_attempt`：

- 任务保存奖励实例、稳定 `fulfillment_no`、类型、状态、下次重试时间；
- 调用流水保存供应商、请求摘要、结果码、外部流水号、耗时和安全错误；
- 第三方幂等键始终使用 `fulfillment_no`，消息 `eventId` 只用于消息消费幂等；
- 远程调用不得持有数据库事务和行锁；
- 调用前短事务将任务从 `PENDING/RETRY_WAITING` 领取为 `PROCESSING`；
- 远程调用结束后用另一个短事务落成功、重试或人工处理结果。

错误分类：

```text
RETRYABLE      网络超时、限流、第三方 5xx
PERMANENT      参数错误、商品编码不存在、账户不存在
UNKNOWN        请求超时且无法确认第三方是否成功
```

`RETRYABLE` 指数退避；`PERMANENT` 进入人工处理；`UNKNOWN` 优先用幂等号查询第三方状态，不盲目再次发放。超过最大尝试次数写入隔离表并产生告警，原 Stream 消息可以 ACK，避免永久毒消息堵塞消费者。

## 11. 模拟外部系统

为券、积分、会员和物流分别定义 Gateway：

```text
CouponGateway
PointsGateway
MembershipGateway
LogisticsGateway
```

每个 Gateway 的模拟实现都保存自己的外部业务记录，并对幂等号建立唯一约束。测试控制接口可以让下一次调用返回成功、业务失败、超时或结果未知，用于验证 LuckyHub 的重试和对账行为。

模拟系统不是直接修改 `user_benefit` 的快捷代码；它必须保持清晰边界，以便未来用真实 HTTP/SDK 适配器替换。

## 12. 一致性与事件流

核心链路：

```text
抽奖/订单本地事务
-> 写业务结果和 Outbox
-> Redis Stream
-> 校验事件身份
-> 创建或唤醒履约任务
-> Worker 领取任务
-> 事务外调用 Gateway
-> 短事务记录结果
-> 成功事件更新权益/订单/物流状态
```

履约入口必须交叉校验事件中的 `benefitId/drawRecordId/prizeId/prizeType` 以及 envelope 中的 `userId/orderId/activityId`。身份不一致属于永久毒消息，不调用外部系统。

数据库是订单、积分、券、会员、奖励和履约任务的事实来源；Redis 只用于消息、缓存和短期协调，不能成为资产最终账本。

## 13. API 边界

用户端最小接口：

- 商品列表和详情；
- 创建现金订单或积分兑换订单；
- 查询订单和模拟支付；
- 查询积分余额与流水；
- 查询用户券；
- 查询会员状态；
- 地址增删改查；
- 为实物奖励确认地址；
- 查询物流轨迹。

管理端最小接口：

- 商品和 SKU 管理；
- 渠道库存分配；
- 券模板和会员产品管理；
- 订单、奖励和履约任务查询；
- 人工重试或标记终止；
- 模拟供应商故障模式控制，仅开发环境开放。

所有接口继续复用 JWT、RBAC、统一错误响应和用户数据范围。管理操作新增细粒度权限码，禁止仅凭前端隐藏按钮控制权限。

## 14. 数据库迁移策略

不修改 V1-V7。从 V8 开始按可独立回滚和验证的领域拆分迁移：

1. V8：统一奖励、商品和 SKU；
2. V9：渠道库存及库存流水；
3. V10：积分账户和流水；
4. V11：优惠券模板和用户券；
5. V12：会员产品和用户会员；
6. V13：订单、订单项、价格快照和支付单；
7. V14：地址、发货单和物流轨迹；
8. V15：履约任务、调用流水和隔离记录。

实际实施中每个迁移在进入下一迁移前完成 schema contract、Mapper 和服务测试，避免一次迁移同时引入全部模块。

## 15. 测试策略

每个子项目使用 TDD，并覆盖：

- 领域单元测试：价格顺序、积分余额、券状态机、会员顺延；
- Mapper/迁移测试：唯一键、CHECK、条件更新和索引；
- 并发测试：库存、锁券、积分扣减、重复回调和重复消息；
- 模拟供应商契约测试：成功、失败、超时、未知结果和幂等查询；
- 端到端测试：抽奖到发券/积分/会员/实物签收；
- 安全测试：越权查询、地址脱敏、回调验签和日志密钥泄漏；
- 对账测试：第三方成功而本地超时、本地成功而回调重复、任务租约过期。

全量验收依赖 MySQL 和 Redis 健康；编译通过不能替代集成测试通过。

## 16. 推荐执行顺序

本设计拆为六个实施计划，每个计划完成后系统都保持可运行：

1. **统一商品、奖励和渠道库存基础**：先消除现有 `PrizeType` 直接承担履约配置的问题；
2. **积分账户与积分商城**：建立资产流水和积分兑换订单最小闭环；
3. **优惠券、会员与现金订单计价**：完成迷你商城交易闭环和模拟支付；
4. **统一异步履约底座与模拟供应商**：解决远程调用、幂等、重试、未知结果、DLQ和对账；
5. **抽奖奖励迁移到统一履约**：让抽奖发放商品、积分、券、会员和抽奖资格；
6. **实物领奖与模拟物流**：完成地址、发货、运单、轨迹、签收和超时未领奖。

不要同时实现六项。每项单独编写实施计划、测试、审查和提交，下一项只依赖已经稳定的接口。

## 17. 设计决策

- 选择“抽奖核心 + 迷你商城”，不建设完整电商平台；
- 选择单体模块化，不提前拆微服务；
- 选择立即购买，不做购物车；
- 选择现金模拟支付，不接真实支付；
- 选择积分全额兑换，不做积分加现金混合支付；
- 选择会员折扣后再计算优惠券；
- 选择总库存按渠道显式分配，不自动跨渠道借用；
- 选择本地模拟外部系统，但所有调用经过可替换 Gateway；
- 选择远程调用与数据库事务分离；
- 选择业务流水和反向冲正，不修改资产历史；
- 选择先完成通用底座，再逐类接入奖励和物流。
