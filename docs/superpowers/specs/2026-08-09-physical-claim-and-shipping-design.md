# LuckyHub 阶段 6：实物领取、地址快照与统一物流设计

> 日期：2026-08-09
>
> 状态：已由用户批准完整设计
>
> 范围：同时覆盖抽奖实物、现金购买实物和积分兑换实物；继续使用本地模拟物流，并保留可替换真实物流供应方的 Gateway 边界。

## 1. 为什么需要阶段 6

阶段 1–5 已经完成商品、渠道库存、积分兑换、现金订单、统一履约和五类抽奖奖励。实物抽奖奖励目前故意停在 `CLAIM_PENDING`，现金实物订单和积分实物兑换也没有收货地址、发货单、运单或物流轨迹。

阶段 6 要补齐真实业务闭环：用户选择地址后，系统冻结不可变地址快照，创建唯一发货单，在领取或交易条件满足后创建 `LOGISTICS` 履约任务，通过模拟物流生成运单并接收物流轨迹。未来接入真实快递时，只替换 `LogisticsGateway`，不修改抽奖、商城和积分领域逻辑。

## 2. 已批准的核心选择

- 同时覆盖抽奖实物、现金购买实物和积分兑换实物；
- 现金实物订单和积分实物兑换在下单时选择地址；
- 抽奖实物在中奖后、领取期限内选择地址；
- 三种来源共用地址快照、发货单、物流任务和轨迹；
- 使用统一发货单模型，不分别复制三套物流逻辑；
- 本地模拟物流继续通过可替换 Gateway 接入；
- 不实现退款、退货、换货、售后或真实快递供应商。

## 3. 总体架构

```text
抽奖实物权益 ─────┐
现金实物订单 ─────┼─> 不可变地址快照 -> shipping_order
积分实物兑换 ─────┘                         |
                                             v
                                  fulfillment_task(LOGISTICS)
                                             |
                                             v
                                  LogisticsGateway
                                             |
                                             v
                              模拟运单 -> 轨迹回调 -> 签收
```

业务模块只负责验证自己的前置条件并调用统一 Shipping 服务：

- 抽奖：权益属于当前用户、类型为实物、状态为 `CLAIM_PENDING` 且未过领取期限；
- 现金订单：商品为实物、下单时冻结地址，支付成功后创建发货单；
- 积分兑换：商品为实物、下单时冻结地址，兑换成功后创建发货单；
- 虚拟商品不接受地址，也不创建发货单；
- Shipping 服务负责来源幂等、任务创建、运单和轨迹；
- Fulfillment Worker 继续在事务外调用 Gateway。

## 4. 数据模型与迁移

只新增 `V17__add_shipping_and_physical_claim.sql`，不修改 V1–V16。

### 4.1 `user_shipping_address`

用户可维护多个地址。主要字段：

- `user_id`；
- 加密的收件人、手机号、省、市、区和详细地址；
- 脱敏收件人、手机号和地区摘要；
- `is_default`、`status`、`version`；
- 创建、修改和软删除时间。

地址删除采用软删除，历史快照不受影响。每个用户最多一个有效默认地址，切换默认地址时使用事务锁保证一致性。

### 4.2 `shipping_address_snapshot`

下单或领奖时创建不可变快照：

- `snapshot_no`；
- `user_id`、来源类型、来源业务 ID；
- 地址密文字段和脱敏展示字段；
- 地址簿原始 ID，仅用于审计，不用于重新读取当前地址；
- 创建时间。

现金订单和积分兑换在下单事务内创建快照。抽奖实物在领取事务内创建快照。后续修改或删除地址簿不会改变快照。

### 4.3 `shipping_order`

统一发货单主要字段：

- `shipping_no`；
- `source_type`：`LOTTERY_BENEFIT/CASH_ORDER/POINTS_REDEMPTION`；
- `source_id`、`target_user_id`；
- `address_snapshot_id`；
- SKU、商品名称、图片和数量快照；
- `fulfillment_no`、承运商、运单号；
- `status`、安全失败摘要；
- 创建、发货、签收、失败和终止时间。

`source_type + source_id` 唯一，保证一个业务来源最多创建一张发货单。`shipping_no`、`fulfillment_no` 和运单号按各自业务约束建立唯一索引。

### 4.4 `shipping_tracking_event`

保存不可变物流轨迹：

- 供应方事件 ID、运单号；
- 标准化事件类型；
- 脱敏或非敏感地点摘要；
- 安全描述、供应方事件时间、接收时间。

供应方事件 ID 唯一，重复事件不重复写入。

### 4.5 `shipping_callback_receipt`

保存回调处理审计：

- `callback_id`、时间戳、nonce 摘要、签名摘要；
- 运单号、事件类型、处理状态和安全错误；
- 创建与完成时间。

`callback_id` 和有效 nonce 建立唯一约束，防止重复处理与重放。

### 4.6 现有表兼容扩展

- `user_benefit` 增加领奖截止时间、领取时间和发货单号；
- `mall_order` 与 `points_redemption_order` 增加可空地址快照和发货关联字段；
- 旧记录保持可查询，新增字段为空；
- 旧接口字段不删除，新增响应字段保持可空；
- V17 为现有 `CLAIM_PENDING` 实物设置“迁移完成后 7 天”的领取期限，避免旧奖品部署后立即过期。

## 5. 状态机

### 5.1 抽奖实物权益

```text
CLAIM_PENDING
├─ 期限内领取 -> CLAIMED -> FULFILLING -> SHIPPED -> DELIVERED
└─ 超时未领取 -> CLAIM_EXPIRED

FULFILLING
├─ 自动重试或未知结果查询 -> FULFILLING
├─ 隔离 -> FULFILLMENT_FAILED -> 管理员重试 -> FULFILLING
└─ 管理员终止 -> FULFILLMENT_TERMINATED
```

用户领取与超时任务锁定同一权益，只允许一个状态转换成功。

### 5.2 统一发货单

```text
READY -> FULFILLING -> SHIPPED -> IN_TRANSIT -> DELIVERED
                    └-> FAILED -> FULFILLING（人工重试）
                              └-> TERMINATED
```

回调只能让状态前进，不能倒退。已经 `DELIVERED` 后收到延迟的 `IN_TRANSIT`，轨迹可以保留用于审计，但发货单仍为 `DELIVERED`。

### 5.3 商城订单和积分兑换

现金订单继续表达支付状态，积分兑换单继续表达积分交易结果。物流状态从关联发货单读取，不把支付、积分资产和物流状态混入同一个字段。虚拟商品没有发货单，旧状态含义不变。

## 6. 地址选择与不可变快照

### 6.1 现金购买和积分兑换

- 创建实物订单时 `addressId` 必填；
- 服务端校验地址属于当前用户且有效；
- 在同一事务中创建业务订单和地址快照；
- 现金订单支付成功后创建发货单和物流任务；
- 积分兑换成功后创建发货单和物流任务；
- 地址簿之后发生任何修改都不会覆盖订单快照。

### 6.2 抽奖领取

领奖请求包含 UUID `requestId` 和 `addressId`。事务内依次：

1. 锁定并验证权益；
2. 验证领取期限和地址归属；
3. 幂等登记领取请求；
4. 创建地址快照；
5. 创建唯一发货单；
6. 创建稳定 `LOGISTICS` 履约任务；
7. 把权益推进到 `CLAIMED/FULFILLING`。

同一请求重复提交返回原结果。已经领取后用另一地址再次请求，不覆盖第一次快照。

## 7. 物流任务与敏感请求装配

稳定履约编号使用 `LOGISTICS-{shippingOrderId}`。`fulfillment_task.request_payload` 只保存：

- `shippingOrderId`；
- SKU 和数量；
- 脱敏收件人、手机号和地区摘要。

任务表、尝试表和模拟供应方表不保存明文地址。Worker 在真正调用 `LogisticsGateway` 之前，通过受控装配器加载发货单、临时解密完整地址，并构造不会输出明文 `toString()` 的敏感请求对象。真实适配器只在内存中持有明文，并通过 TLS 发送。

本地模拟物流仍只持久化脱敏请求摘要和模拟运单号。未来替换真实 Gateway 时，履约任务、重试、对账、隔离和业务来源状态机不改变。

## 8. 用户与管理 API

### 8.1 用户地址和物流

```http
POST   /api/shipping/addresses
GET    /api/shipping/addresses
PUT    /api/shipping/addresses/{addressId}
DELETE /api/shipping/addresses/{addressId}
PUT    /api/shipping/addresses/{addressId}/default

POST   /api/benefits/{benefitId}/claim
GET    /api/shipping/orders/{shippingNo}
GET    /api/shipping/orders/{shippingNo}/tracking
```

领奖示例：

```json
{
  "requestId": "3eb67b1c-92c3-4a41-a652-dc815c23b56e",
  "addressId": 18
}
```

用户只能操作自己的地址、领取自己的权益并查询自己的包裹。

### 8.2 商城接口兼容调整

- 创建现金订单和积分兑换请求增加可空 `addressId`；
- 实物商品必须填写，虚拟商品必须不填写；
- 查询结果增加可空快照摘要、发货单号和物流状态；
- 旧调用方查询虚拟商品和旧数据保持兼容。

### 8.3 管理接口

```http
GET  /api/admin/shipping/orders
GET  /api/admin/shipping/orders/{shippingNo}
POST /api/admin/shipping/orders/{shippingNo}/retry
POST /api/admin/shipping/orders/{shippingNo}/terminate
POST /api/admin/simulators/logistics/{fulfillmentNo}/events
```

管理列表默认脱敏。重试和终止复用阶段 4 的履约状态约束，`PROCESSING` 和 `SUCCEEDED` 等不安全状态不能被强制终止。

## 9. 物流回调

真实物流回调入口使用时间戳、nonce 和 HMAC-SHA256 验签，不依赖用户 JWT。处理顺序：

1. 校验允许时间窗口；
2. 校验 nonce 未使用；
3. 校验 HMAC；
4. 以 `callbackId` 幂等登记；
5. 按运单号锁定发货单；
6. 校验状态推进规则；
7. 写不可变轨迹；
8. 更新发货单和来源投影；
9. 同一事务提交处理结果。

模拟物流管理接口可生成 `PICKED_UP`、`IN_TRANSIT`、`OUT_FOR_DELIVERY` 和 `DELIVERED`，但必须走与真实回调相同的验签、幂等和状态处理路径。

## 10. 隐私与密钥

- 地址使用应用层 AES-256-GCM 加密；
- 每次加密生成随机 nonce，并在密文封装中记录密钥版本；
- 独立密钥由环境变量提供，不写入数据库或 Git；
- 测试和验收脚本注入专用测试密钥；
- 生产环境缺少密钥时启动失败；
- 用户和管理员默认只看到脱敏姓名、手机号和地区；
- 日志、事件、异常、履约 payload、尝试记录和模拟表禁止明文个人信息；
- 敏感请求对象使用安全摘要，不依赖自动生成的 record/Lombok `toString()`；
- 安全错误只保存枚举原因、稳定错误码和不含个人信息的短摘要。

展示示例：

```text
张* / 138****5678 / 浙江省杭州市余杭区***
```

## 11. 超时、补偿与人工恢复

- 新抽奖实物默认领取期限为 7 天，可通过配置调整，并在权益上冻结截止时间；
- 定时任务扫描 `CLAIM_PENDING` 且已过期的权益；
- 状态变更和库存回补使用同一数据库事务；
- 库存回补业务号固定为 `CLAIM-EXPIRE-{benefitId}`，通过库存流水唯一约束幂等；
- 回补失败则事务回滚，下次调度继续尝试；
- 已领取后的物流失败不自动退库存；
- 自动重试和未知结果查询继续复用阶段 4；
- 隔离后管理员可重试，终止必须记录操作者和安全原因；
- 阶段 6 不处理退款、退积分、退货、换货或售后。

## 14. 完成标准

阶段 6 完成时：

- 三种实物来源都能选择属于当前用户的地址并冻结不可变快照；
- 每个来源只创建一张发货单和一个稳定物流履约任务；
- 模拟物流可以生成运单、推进轨迹并最终签收；
- 领取、支付、兑换、任务和回调重复执行均保持幂等；
- 超时未领取能够安全回补库存；
- 物流失败能够自动重试、查询对账、隔离、人工重试或终止；
- 明文地址和手机号不进入日志、事件、履约账本、模拟表或安全错误；
- V1–V17 空库迁移、集中验收、全量回归、可执行 JAR 和 OpenAPI 冒烟全部通过。

## 15. 明确不做

- 不修改已发布的 V1–V16；
- 不改变阶段 5 的奖励快照和身份交叉校验；
- 不在实物中奖时提前创建物流任务；
- 不接入真实快递账号；
- 不实现退款、退积分、退货、换货或售后；
- 不建设购物车、多仓库、运费计算或复杂配送路由；
- 不把模拟物流写死到业务服务；
- 不把明文地址、手机号、密钥、原始供应方响应或完整异常写入持久化记录。
