# EligibilitySnapshot 教学文档设计说明

## 1. 文档目标

新建一篇面向 Java 与后端开发学习者的中文教学文档，围绕下面这行真实代码展开：

```java
DrawEligibilityService.EligibilitySnapshot snapshot =
        eligibilityService.load(command.activityId());
```

文档不能停留在 Java 语法解释，而要让读者沿着一次抽奖请求的实际执行顺序，理解：

- 程序为什么需要先加载抽奖资格和配置；
- 为什么要把返回结果保存在 `snapshot` 局部变量中；
- `EligibilitySnapshot` 是怎样从数据库数据组装出来的；
- 单抽和十连抽后续怎样复用这份快照；
- 快照能够保证什么，不能保证什么；
- 以后遇到相似场景时，如何自行设计这种只读业务快照。

## 2. 目标读者与讲解方式

主要读者是正在通过 LuckyHub 项目学习 Spring Boot、Java `record`、业务编排和并发控制的初学者。

采用“执行流程优先”的讲解方式：从 `LotteryServiceImpl.draw()` 进入，程序执行到哪一行，就解释该行遇到了什么问题、为什么需要当前类型或服务，以及返回的数据接下来流向哪里。Java 语法穿插在执行流程中解释，不单独堆砌概念。

所有结论必须对应当前仓库中的真实代码，不把计划中的功能或常见做法误写成已经实现的行为。

## 4. 正文章节

正文按以下顺序组织：

1. 从一次抽奖请求进入 `LotteryServiceImpl.draw()` 开始；
2. 逐部分拆解目标代码的 Java 语法；
3. 用“没有快照会怎样”解释设计动机；
4. 进入 `DrawEligibilityServiceImpl.load()`，按照真实执行顺序逐行解释；
5. 解释 `EligibilitySnapshot` 的五个字段；
6. 解释嵌套 `record`、紧凑构造器与 `List.copyOf`；
7. 跟踪快照进入额度预占和 `DrawExecutionContext`；
8. 跟踪奖品快照进入权重算法、库存条件扣减和结果落库；
9. 使用一个十连抽示例串联完整生命周期；
10. 区分内存配置快照、数据库事务快照和结果历史快照；
11. 说明配置被管理员并发修改、奖品并发售罄时的实际行为；
12. 给出断点调试步骤、单元测试阅读方法和可复用的设计步骤；
13. 汇总常见误解和检查题。

## 5. 必须讲清楚的代码事实

- `EligibilitySnapshot` 是 `DrawEligibilityService` 中声明的嵌套 `record`。
- 当前实现每个新抽奖订单调用一次 `load(activityId)`；幂等请求已存在时不会重新加载。
- `load` 查询活动、活动奖品关系和奖品信息，并检查活动状态与时间窗口。
- 快照包含 `activityId`、`dailyLimit`、`noWinWeight`、`prizes` 和 `snapshotTime`。
- `List.copyOf(prizes)` 防止快照中的奖品列表在创建后被增删，但不能把它描述成数据库锁。
- 十连抽的十次循环使用同一个 `DrawExecutionContext` 和同一组奖品配置。
- 快照中的库存是候选筛选数据，不是最终库存真相；最终中奖仍以数据库条件扣减成功为准。
- 候选奖品在真正扣减时已经无库存，会转成未中奖。
- 当前请求加载快照后，即使管理员修改活动配置，该请求也继续使用已加载的数据；后续新请求才重新读取。
- 该对象没有作为一个整体写入数据库，也不是 Redis 缓存，更不是 MySQL 的一致性读快照。

## 7. 内容边界

本次只新增教学文档和文档入口，不修改 `EligibilitySnapshot`、抽奖算法、数据库结构或接口行为。

文档会指出当前设计的边界，但不借此扩展缓存、版本号、配置锁、Kafka 等新功能。发现代码问题时，只在文档中如实说明，除非用户另行要求修改实现。

## 8. 验收标准

完成后的文档应让没有阅读过抽奖模块源码的学习者能够正确回答：

1. 目标代码的左侧类型、变量和右侧方法调用分别是什么意思？
2. 为什么不是在十次抽奖循环中重复查询数据库？
3. 五个快照字段分别来自哪里、被谁使用？
4. 为什么 `List.copyOf` 仍然不能防止超卖？
5. 管理员修改配置或其他用户抢完库存时，当前请求会发生什么？
6. 如何在另一个业务中设计类似的不可变输入快照？

文档不得包含占位符、与源码不一致的结论或无法定位的虚构类名。
